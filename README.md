# GOST Restreamer — плагин OBS

Нативный плагин OBS Studio для управления отдельным сервером
[GOST Restreamer](https://github.com/GregoryGost/gost-restreamer): компактный Dock
и одно расширенное окно управления и настроек. OBS создаёт один штатный
медиапоток; плагин предоставляет интерфейс, REST/SSE-клиент и согласует команды.

Требования, границы компонентов и критерии приёмки описаны в
[архитектуре проекта](gost-obs-plugin-architecture.md). Целевой стек: Windows
10/11 x64, OBS Studio 33.0.1, C++20, Qt 6 Core/Widgets/Network, MSVC и CMake.
Реализован каркас плагина: Dock, единственное повторно открываемое окно с шестью
разделами, наблюдение за OBS Profile и состоянием штатной трансляции, локализации
`ru-RU` и `en-US`. Управление сервером, REST/SSE-клиент и медиакоманды относятся
к следующим этапам. Установщик пока не создан.

## Состояние проверки

Штатный configure, сборка DLL и тестовых программ в `RelWithDebInfo`/`Release`
и установка в staging прошли. CTest: локальный preset — 1/1, оба полных — 2/2,
включая три GET к backend. Проверены x64 PE, девять экспортов OBS, локализации
и совпадение новой раскладки staging/install.

Прежнее зависание MSBuild при повторной проверке не воспроизвелось. Следующая
остановка была локализована в CMake: OBS SDK повторно скачивал уже имеющиеся
пакеты. Bootstrap теперь проверяет SHA256 и передаёт архивы в собственный кеш
OBS. Версии инструментов и зависимости сохранены.

Приёмка каркаса T01 завершена: восемь запусков изолированной OBS 33.0.1
(обычный и portable режимы, `ru-RU`/`en-US`, по два запуска) прошли с кодом 0.
Проверены шесть разделов, единственное повторно используемое окно, его
фактическая активация, сворачивание и закрытие, наблюдение за профилем OBS
и остановленной трансляцией, восстановление видимости и координат плавающего
Dock. Обычный режим фактически загрузил DLL из нового каталога ProgramData.
Временное глобальное размещение после проверки удалено; пользовательские
настройки OBS не использовались, трансляции не запускались.

Исходная причина прежнего зависания MSBuild отдельно не установлена.
Итоги и границы проверки записаны в [профиле проекта](CODEX_PROJECT.md).

## Сборка Windows x64

Нужны CMake 3.28+ и Visual Studio Build Tools 2022 с v143 и Windows SDK
10.0.26100.0. Локально обнаружены CMake/CTest 3.31.8, MSVC 14.44.35207 и OBS
33.0.1 с Qt 6.11.1. Visual Studio IDE не требуется.

```powershell
cmake --preset windows-x64
cmake --build --preset windows-x64
cmake --build --preset windows-x64-release
cmake --install build_x64 --config RelWithDebInfo
```

Configure загружает закреплённые зависимости в `.deps/`, проверяет SHA256
и готовит OBS SDK внутри проекта. Глобальная установка SDK не нужна.
Конфигурация разработки — `RelWithDebInfo` с символами; распространение —
`Release`. Обе используют динамический CRT и C++20. Нативный генератор Visual
Studio не создаёт `compile_commands.json`; VS Code получает контекст через
CMake Tools (`.vscode/settings.json`).

Согласованная новая раскладка OBS 33:

```text
build/install/gost-restreamer-obs-plugin/
  gost-restreamer-obs-plugin.dll
  gost-restreamer-obs-plugin.pdb    (если доступны символы)
  data/locale/ru-RU.ini
  data/locale/en-US.ini
```

Ту же внутреннюю структуру создаёт сборка в
`build_x64/rundir/<configuration>/gost-restreamer-obs-plugin/`.
При обычной установке родитель — `%ProgramData%/obs-studio/plugins/`,
при portable — `<OBS>/plugins/`. CMake по умолчанию устанавливает только
в рабочий staging проекта. Полный пакет и установщик относятся к выпуску.

## Короткие проверки

Все последующие проверки выполняются только внутри workspace проекта.
AppData и ProgramData для них не используются. Конфигурация OBS, плагины,
кеши, временные файлы и журналы остаются в каталогах проекта; `TEMP`/`TMP`
тестовых процессов также направляются внутрь workspace.

```powershell
ctest --preset windows-x64
ctest --preset windows-x64-release
ctest --preset windows-x64-offline
```

Локальные тесты Qt Test используют подмену OBS Frontend API и настоящий
`QApplication`: проверяют наблюдаемое состояние, два представления, повторное
открытие окна, порядок регистрации и синхронное завершение, ошибки инициализации.
Offscreen-проверки не подтверждают Windows DPI и фокус настоящего OBS.

Обычные тестовые presets автоматически читают backend
`http://192.168.88.8:8080`: только `GET /api/v1/health/live`,
`GET /api/v1/health/ready` и `GET /api/v1/system/capabilities`,
с ограничением времени и размера ответа, без перенаправлений и повторов.
Они не запускают трансляции, не меняют сервер и не подключают SSE.
`windows-x64-offline` исключает серверную проверку. Для другого адреса:

```powershell
$env:GOST_TEST_BACKEND_URL = 'http://192.168.88.8:8080'
ctest --test-dir build_x64 -C RelWithDebInfo --output-on-failure
```

Без адреса серверный тест явно пропускается; недоступный заданный сервер
означает отказ проверки. Значение URL используется только тестами, адрес
продуктового подключения будет настраиваться в последующих этапах.

`tests/integration/Test-PluginArtifact.ps1` проверяет PE x64, экспорты OBS,
совпадение DLL и локализаций со сборкой и новую раскладку.
`tests/integration/Test-PortableObs.ps1` запускает свежую копию OBS 33.0.1
внутри workspace с пустым профилем без источников и штатно её закрывает.
Для последующих запусков используется только `-Mode Portable`: конфигурация
находится в `config/`, плагин — в `plugins/` этой копии внутри проекта.
Режим `-Mode Normal` и прежние помощники ProgramData больше не запускаются.
Установочную структуру проверяем в staging проекта. Описанная выше приёмка
обычного режима T01 относится к уже выполненной исторической проверке.

Для нативной проверки нужен интерактивный рабочий стол. Если Windows запрещает
получение фокуса через API, в течение 20 секунд щёлкните один раз по основному
окну нового тестового OBS с профилем `Isolated`; последующие действия выполняет
сценарий. В среде агента sandbox может скрывать активное окно, поэтому
проверка фокуса выполняется вне него с сохранением файловой изоляции workspace.
Результаты, исходный вывод проверки интерфейса и журналы сохраняются внутри
тестовой portable-копии.
Физическое перетаскивание Dock, размеры и полный набор DPI-сценариев остаются
отдельной проверкой выпуска.

## Происхождение шаблона и зависимостей

Импортирован целиком официальный
[OBS Plugin Template](https://github.com/obsproject/obs-plugintemplate/tree/3e7d7ac3b5342cd7d9b88890b9c70b472d1520fc),
ревизия `3e7d7ac3b5342cd7d9b88890b9c70b472d1520fc`, без PR #172.
Существовавшие README и `.gitignore` сохранены и дополнены. Собственная адаптация
задаёт имя, C++20, Windows x64, зависимости OBS 33.0.1, UI и новую раскладку.
Импортированные сценарии других платформ, CI и выпуска пока не прошли адаптацию
и приёмку; поддержка macOS/Linux не заявляется. Лицензия шаблона — [GPL-2.0](LICENSE).

OBS SDK и Qt SDK берутся из официальных архивов OBS 33.0.1 и `obs-deps`
`2026-10-23`; URL и SHA256 закреплены в [buildspec.json](buildspec.json).
Официальный пакет OBS не содержит Qt Test. Для тестов отдельно используется
официальный Qt Base 6.11.1 MSVC 2022 x64, опубликованный в репозитории Qt;
загрузка с официального зеркала и SHA256 закреплены в
[qttest.cmake](cmake/windows/qttest.cmake). Его runtime применяется только
к тестовым процессам и не устанавливается рядом с DLL плагина.

## Работа с Codex

Подключён выбранный набор
[agent-projects-tools](https://github.com/GregoryGost/agent-projects-tools/tree/ff4393f50c7d2e47cc03197e6e45ed087c89c954).
Сначала агент читает [AGENTS.md](AGENTS.md), затем обязательную
[маршрутизацию](.codex/rules/request_routing.md) и
[профиль проекта](CODEX_PROJECT.md). Профиль задаёт точные активные материалы,
границы делегирования, язык, доступность инструментов и правила приёмки.

| Область | Подключённые материалы |
| --- | --- |
| Маршрутизация и общие правила | Request routing, проверка зависимостей, координация субагентов, source code hygiene, Git |
| Техническая документация | Context7 с проверкой применимой версии и переходом к официальным источникам при необходимости |
| Язык пояснений рядом с кодом | `comment-language-audit`; комментарии, описания тестов, Git и собственная документация — на русском |
| C++ | Core, стиль, CMake, тестирование; стандарт проекта C++20 |
| Qt 6 | Core, Widgets, Testing и Quick/QML |

QML активирован для будущих задач по выбору владельца. Текущий интерфейс
проектируется на Widgets; подключение материалов не добавляет QML runtime,
исходники или новые окна. Версии Qt/OBS SDK и реальные команды сборки
закреплены в проекте; фактическую инвентаризацию см. в профиле.

В [.codex/agents/](.codex/agents/) находятся девять специализированных ролей:
два независимых архитектора, исследователи кода и документации, исполнители
простых и сложных изменений, тестировщик, специалист по ревью и диагност сложных ошибок.
Модели и effort перечислены в профиле. Выбранные роли используются только для
разрешённой работы с исполняемым кодом/тестами; инструкции и документацию
обрабатывает основной агент. Для архитектурных задач действует согласование
единой редакции обоими архитекторами; тесты и ревью проверяют стабильный снимок.
Архитектор БД не подключён: SQLite и миграции принадлежат отдельному backend.

### Локальная конфигурация

`.codex/config.toml` игнорируется Git и хранит локальные настройки, включая
аутентификацию MCP. Пример без секретов:
[.codex/config.example.toml](.codex/config.example.toml). Если локального файла
ещё нет, его можно создать из примера в PowerShell:

```powershell
if (-not (Test-Path -LiteralPath .codex/config.toml)) {
    Copy-Item -LiteralPath .codex/config.example.toml -Destination .codex/config.toml
}
```

Если файл существует, объедините нужные параметры, сохранив свои настройки.
В доверенном проекте актуальный Codex обнаруживает отдельные TOML-файлы ролей
из `.codex/agents/`; формат описан в
[официальной документации субагентов](https://learn.chatgpt.com/docs/agent-configuration/subagents).
Загрузка project config зависит от доверия к проекту и ограничений клиента;
доступность моделей/effort проверяется в конкретном аккаунте. Пример не меняет
модель уже работающей сессии.

Полные пакеты навыков с references находятся в [.agents/skills/](.agents/skills/).
Их наличие не заменяет активацию и проверку hard dependencies из профиля.
SDK, расширения редактора и дополнительные MCP этой интеграцией не устанавливаются.

### Обновление набора

Обновление выполняется явно: сопоставьте изменения upstream,
сохраните проектные дополнения `AGENTS.md`,
согласованно обновите bootstrap, rules, выбранные роли и полные пакеты навыков,
затем перепроверьте профиль, зависимости, ссылки и TOML. Не активируйте новые
материалы только из-за их появления в upstream.
