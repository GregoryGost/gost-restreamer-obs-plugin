## 1. Назначение и цели

`gost-restreamer-obs-plugin` — нативное расширение OBS Studio, предоставляющее два представления: компактный Dock внутри OBS и **одно расширенное окно «GOST Restreamer — Управление и настройки»**, открываемое через «Сервис → GOST Restreamer». Веб-панель не требуется. Пользователь работает внутри OBS: выбирает сервер и Stream, запускает и завершает эфир, переключает fallback, контролирует группы и назначения, редактирует настройки и видит диагностические показатели.

Ключевой сценарий:

- игровой ПК Windows с OBS и RTX 4080 SUPER создаёт **один штатный исходящий AV1/AAC-поток 2560×1440, 60 FPS, SDR**;
- Go-сервер принимает этот поток по Enhanced RTMP, поддерживает Session и fallback, раздаёт совместимые группы через `copy` либо серверный FFmpeg/NVDEC/NVENC;
- YouTube может получать AV1 без повторного кодирования, а VK/другие платформы — совместимые H.264-профили. Это пример конфигурации backend, а не жёстко зашитый список площадок;
- плагин **не** захватывает кадры, **не** кодирует второй поток, **не** создаёт собственные media output и **не** повторяет логику рестриминга.

### Основные требования

1. **Ровно два основных окна:** компактный Dock без вкладок и отдельное расширенное окно с навигацией по функциональным разделам. Пункт «Сервис → GOST Restreamer» открывает расширенное окно; его повторное открытие активирует существующий экземпляр.
2. В настройках плагина — **адрес сервера (HTTP API)**, параметры локального подключения, интерфейса и уведомлений; RTMP настраивается штатными средствами OBS.
3. Использование штатного streaming service/output OBS: RTMP Server и Stream Key **вводятся в «OBS → Настройки → Трансляция»**, плагин не меняет их автоматически. В расширенном разделе **«Потоки»** `Stream.publication_key` выбранного серверного Stream **доступен для просмотра и копирования в любой момент** (по умолчанию замаскирован); это справочное значение для ручной вставки в OBS, а не второй редактор OBS streaming service.
4. Обычный эфир запускается штатной кнопкой OBS; плагин подхватывает созданную сервером Session. Dock предоставляет серверные Pause/Resume и «Завершить эфир» (внутренний StopAll), а также отдельные и пакетные Start/Stop/Restart показанных выходов. Команды выходов не включают и не останавливают OBS. Отдельный UI предварительного запуска заглушки отложен до согласования; существующие команды API достаточны.
5. На Dock — критические состояния OBS, входа и каждого выхода, базовая статистика OBS (FPS, среднее время рендеринга, пропуски рендеринга/кодирования/сети, битрейт) и сервера (принятые FPS/битрейт, выходные битрейты, reconnect/потери очереди). Сброс видимых накопительных счётчиков — только локальная точка отсчёта.
6. В расширенном окне — Streams/Destinations/Groups, полный versionless профиль dev.8, Fallback, диагностика и настройки. Ключи и адреса доступны для показа/копирования. Заглушка содержит цифровую тишину выбранной поддержанной аудиопривязки; готовность поколения и Session проверяется раздельно.
7. Корректная работа при обрывах OBS, REST/SSE, остановке Go-сервера и повторном запуске плагина.
8. Основная разработка в **Visual Studio Code**; нативная Windows-сборка и отладка MSVC.

### Границы

- **OBS:** сцены, источники, аудио, аппаратное кодирование, штатный streaming output, локальный профиль OBS.
- **Плагин:** пользовательский интерфейс, сетевой клиент, оркестрация действий OBS и серверных команд, локальные настройки, наблюдение.
- **Go backend:** постоянные Stream/Destination/Profile/Group/Fallback настройки, SQLite, доступ к media ingest, подготовка fallback, независимые Output, процессы FFmpeg, ретраи и мониторинг.
- **Площадки:** RTMP/RTMPS-соединения устанавливаются backend; плагин не подключается к ним напрямую и не подтверждает, что внешний видеоплеер действительно показывает картинку.

## 2. Актуальный статус и границы backend

`gost-restreamer` развивается самостоятельно; его исходный код в ветке `develop` содержит **исполняемую точку входа приложения**, конфигурацию инсталляции и собираемые артефакты для Debian. HTTP API, SessionManager, RTMP ingest, fallback и мониторинг сведены в общую сборку. **T11 закрыта владельцем 9 ноября 2026 года** после основного прогона с настоящим OBS, сервером на VM Debian 13.4 / RTX A1000 и YouTube/VK/Twitch; это подтверждение конкретного медиасценария, а не готовность отдельного Windows-плагина и всех управляющих сценариев.

Проверенные интеграционные факты:

- Маршруты API: `/api/v1`, REST/SSE без авторизации в согласованном **локальном контуре владельца**. Отдельный ключ Stream служит только для RTMP-публикации.
- **Чтение ключей в контракте `103d839`:** конфигурационные POST/GET/PATCH и все списки возвращают `Stream.publication_key`, `Destination.stream_key` и полный `Destination.endpoint`; те же поля доступны во вложенных исторических снимках Session/Output. Пустой `stream_key` допустим. В прежнем dev.5 были лишь `*_configured`; отсутствующее поле старого ответа явно недоступно, `null` или неверный тип — ошибка контракта. Значения сохраняются точно в RAM, без нормализации URL и записи в настройки/журнал. Карточки показа/копирования относятся к следующему этапу редакторов.
- Команды Session/Output асинхронны: `202 Accepted` — принятие; `GET /commands/{commandId}` — действительный результат. Конфигурации изменяются с `expected_revision` и контролем `409`.
- Оперативные наблюдения хранятся в RAM; начальное чтение `GET /events/snapshot` и продолжение `GET /events` (SSE). История и квитанции долговечны в SQLite.
- Медиопоток создаёт **штатный OBS streaming output**. Конфигурация RTMP Server/Stream Key принадлежит OBS. Плагин не задаёт собственного RTMP ingest и не меняет streaming service.
- **Автозапуск dev.7:** правильная RTMP-публикация при отсутствии активной Session запускает её со всеми включёнными назначениями; плагин наблюдает результат через REST/SSE. Поведение при готовности, остановке и переподключении описано в разделе 2.3.
- Рестример поддерживает полный профиль dev.8: явный `live_audio_mode`, полный `encoding` без версии и UTF-8 настройки. Видео — H.264/AV1/HEVC/VP9 по матрице, звук — AAC LC/Opus/FLAC/MP3/AC-3; правила полного редактора — раздел 7.1. Историческая семантика dev.5 описана отдельно в 2.2.
- Новые ACK-показатели выходов уже есть в `OutputMetricsDTO` в REST/SSE. Их нельзя считать доказательством сбоя воспроизведения.
- **Пакетного `restart-all`, отдельного `restart` для Output и API сброса накопительных метрик нет.** Такие пользовательские действия принадлежат контроллеру плагина; он не может утверждать, что сервер выполнил их атомарно.

### 2.1 Проверенный медиосценарий и его границы (T11)

В [целевой приёмке 8–9 ноября 2026 года](https://github.com/GregoryGost/gost-restreamer/blob/develop/docs/media-contracts.md) зафиксированы: подготовка трёх fallback-вариантов под фактические профили, работа fallback **до** подключения OBS, переход трёх групп в LIVE, подтверждённые владельцем изображение и звук на YouTube/VK/Twitch. Окно измерений — **602,539 секунды** (около 10 минут), **31 успешный REST-снимок** с интервалом около 20 секунд. Выходы оставались `PUBLISHING`, очереди — пустыми; новых локальных потерь, reconnect и измеримых аномалий ACK в этом окне не отмечено.

После остановки OBS три группы перешли в `READY/FALLBACK`, а выходы остались `PUBLISHING` **без переподключения**; серверная Session завершилась лишь по отдельной команде владельца. Это наблюдение подтверждает принцип раздельного состояния OBS/Session/Outputs, уже принятый для Dock. Использованные CBR-профили (10/12/6 Мбит/с, AAC LC 48 kHz stereo 160 кбит/с, GOP 120) — **условия проверенного опыта, не универсальные пресеты и не жёсткие параметры UI**.

**T11 не подтверждает:** управляемые отказы/зависания FFmpeg, медленные выходы и их reconnect, `Publisher Override`, pause/resume, динамическое добавление/удаление выходов, независимое изменение FPS, контрольную сверку REST/SSE, точные A/V-временные шкалы/задержку, полный cleanup и устойчивость за пределами принятого окна. Эти сценарии остаются самостоятельными требованиями приёмки плагина и/или серверной интеграции. Версии установленных бинарников/драйвера в исходном наблюдении отдельно не перепроверялись.

**Историческая граница T11:** описанный успешный эфир относится к сборке до T15. Он подтверждает конкретный медиосценарий, но не должен выдаваться за испытание нового LIVE-аудиорежима и беззвучного генератора заглушек. Существующие метрики ACK, SSE и идемпотентные квитанции остаются в контракте; изменения T15 затрагивают профиль и проверку пригодности fallback, а не вводят новые маршруты управления.

### 2.2 Изменения T15 в поставке `v0.1.0-dev.5`

Поставка `v0.1.0-dev.5+ccbca60acb5b` соответствует коммиту `ccbca60acb5bf90322342ae0b59665a30f9e97f6` и [успешному CI №12](https://github.com/GregoryGost/gost-restreamer/actions/runs/42614473484). В `develop` опубликован dev-тег, файлы `.deb`/`.tar.gz`/`SHA256SUMS` доступны в Actions Artifact `13671938154` (с ограниченным сроком хранения). Dev GitHub Release не создаётся. Успех CI подтверждает пройденную область проверок поставки, **но не новый реальный эфир на Windows/OBS 33 и не целевой VM-прогон T15**.

Требования к плагину, подтверждённые [обновлённым API-контрактом](https://github.com/GregoryGost/gost-restreamer/blob/develop/docs/api-contracts.md#полный-профиль-кодирования):

- **Видео и LIVE-аудио выбираются независимо.** `profile.mode` по-прежнему задаёт `copy/transcode` видео; новое поле верхнего уровня **`profile.live_audio_mode`** задаёт `copy/transcode` для AAC. В новых профилях отсутствие поля при создании означает `copy`, даже если видео перекодируется. У видео `mode=copy` допустимо только `live_audio_mode=copy`.
- При LIVE-аудио `copy` пригодный AAC из OBS передаётся без повторного кодирования; должны совпадать ожидаемые AAC-профиль, sample rate, число и расположение каналов. При несовместимости группа остаётся на пригодной заглушке, автоматического переключения в `transcode` нет. Подробная причина находится в серверном журнале, публичный API не обещает отдельный код «ошибка AAC-совместимости».
- **Заглушка всегда беззвучна:** из изображения и из видео со звуковой дорожкой сервер создаёт AAC-тишину по профилю. `audio_encoding`, `encoding.audio_encoder` и `encoding.audio_custom` всегда относятся к звуку заглушки, а к LIVE — только если аудио явно `transcode`. Непосредственно после LIVE→FALLBACK может кратковременно звучать остаток прежнего звука в декодере получателя; универсальный предел такого остатка не заявлен.
- **Прежние профили сохраняют поведение.** Отсутствующее у исторической записи поле `live_audio_mode` означает наследуемую обработку (при видео `copy` — AAC copy, при видео `transcode` — прежний AAC transcode). GET и изменение только имени не переводят старый профиль на новое поведение. После явного задания `live_audio_mode` полная замена `profile` обязана включать это поле; `null`, пустое и неизвестное значение запрещены. Внутренняя версия сохранения профиля 3 — не `encoding.version` и не поле HTTP DTO.
- **Старые READY-варианты fallback не пригодны для нового генератора.** Версия беззвучного рецепта — `fallback-fmp4-silent-v2`. После обновления со старого генератора пользователь выполняет `rebuild` до эфира, без повторной загрузки оригинала, затем проверяет новое поколение и старт Session. Старое current может оставаться в истории и показывать `READY`, но по одному публичному DTO версия генератора не определяется. Ошибка rebuild сохраняет текущую запись, **не делает её воспроизводимой новой версией**. Уже закреплённые OutputSnapshot не получают свежий вариант автоматически.

Остальные принятые решения плагина — два окна, штатный RTMP OBS, REST/SSE, квитанции, одиночные и массовые операции, клиентский сброс статистики — изменений не требуют.

Основа проверки: [контракт API](https://github.com/GregoryGost/gost-restreamer/blob/develop/docs/api-contracts.md), [руководство OBS-клиента](https://github.com/GregoryGost/gost-restreamer/blob/develop/docs/obs-client-guide.md), [контракт приложения](https://github.com/GregoryGost/gost-restreamer/blob/develop/docs/application-contracts.md), [мониторинг](https://github.com/GregoryGost/gost-restreamer/blob/develop/docs/monitoring-contracts.md).

### 2.3 Автозапуск при публикации OBS в dev.7

Источники — [инструкция OBS](https://github.com/GregoryGost/gost-restreamer/blob/067388bc1e36ac5220e001c72c47220ef0b72173/docs/obs-client-guide.md#запуск-и-асинхронные-команды), [допуск SessionManager](https://github.com/GregoryGost/gost-restreamer/blob/067388bc1e36ac5220e001c72c47220ef0b72173/internal/session/obs.go) и [его тесты](https://github.com/GregoryGost/gost-restreamer/blob/067388bc1e36ac5220e001c72c47220ef0b72173/internal/session/obs_admission_test.go). Это подтверждение контракта, не отчёт о приёмке плагина.

- Сервер проверяет постоянный ключ Stream до создания Session и команды запуска. Если активной Session нет, публикация запускает все `Destination.enabled=true`. Заглушки должны быть подготовлены заранее: подключение OBS не выполняет upload/rebuild.
- При `STARTING` публикация ждёт готовности выбранной Session; при `RUNNING` использует её, сохраняя паузу, остановленные и отсоединённые выходы. При `STOPPING` текущая публикация отклоняется. Один запрос допуска не переходит к следующей Session после остановки выбранной; следующая отдельная публикация после завершения stop может создать новый эфир.
- Допуск ждёт фактической готовности локальных групп и fallback. Подключения к площадкам независимы; принятие входа не подтверждает воспроизведение у зрителя. Таймаут или разрыв подключения OBS после принятия запуска не отменяет серверную Session: она может продолжать работать с заглушкой.
- Серверная остановка не запрещает будущие публикации с тем же ключом. Для полного завершения нужно прекратить штатную передачу и переподключение OBS, затем остановить точную Session. Плагин не объявляет общий успех только по серверной квитанции, если остановка OBS не подтверждена.
- После рестарта сервера прежняя Session сама не возобновляется, но новая публикация, включая автоматическое переподключение OBS, может создать новую Session. Восстановление REST/SSE самим плагином не отправляет `start` и не останавливает OBS.
- Предварительный `POST /streams/{id}/start` сохраняется для передачи заглушки до OBS и явного выбора назначений. Его интерфейс в плагине отложен до отдельного согласования; серверный workflow не вызывает запуск OBS. Обычная публикация присоединяется к уже подготовленному запуску без сброса его намерений.

Сравнение dev.6 → dev.7 не выявило ломающих изменений полей REST/SSE; изменились сценарии допуска OBS. Контрактная fixture обновлена по схеме фактического сервера от 13.11.2026 и сверена с исходниками dev.7. Происхождение и SHA256 сохранены в `tests/fixtures/backend/provenance.json`; версия API не подтверждает commit установленного серверного бинарника.

## 3. Стек и совместимость

| Составляющая | Выбор / правило |
| --- | --- |
| Целевая ОС | Windows 10/11 x64; 32-битные версии не поддерживаются |
| Целевая версия OBS | 33.0.1 как проверяемая базовая версия; совместимость с новыми релизами подтверждается тестами |
| Язык | C++20 |
| Плагин | Нативный модуль OBS через `libobs` и `obs-frontend-api` |
| UI | Qt 6 Widgets: один Dock и одно расширенное окно с внутренними страницами/редакторами |
| HTTP/SSE | Qt Network: `QNetworkAccessManager`, `QNetworkReply` |
| JSON | Qt JSON (`QJsonDocument`, `QJsonObject`) с отдельной валидацией DTO |
| Сборка | CMake; Windows/MSVC (Build Tools), Ninja или генератор Visual Studio через CMake Presets |
| Разработка | **Visual Studio Code** + расширения C/C++, CMake Tools, CMake |
| Отладка | `cppvsdbg` либо отладочная интеграция CMake Tools с MSVC |
| Зависимости OBS | Официальный [obs-plugintemplate](https://github.com/obsproject/obs-plugintemplate), с адаптацией под OBS 33.0.1 |
| Публикация | ZIP и Windows installer; расширение устанавливается локально в OBS |

В базовом OBS Plugin Template параметры `ENABLE_FRONTEND_API` и `ENABLE_QT` выключены и должны быть включены; дополнительно подключается `Qt6::Network`, исходник `plugin-main.c` заменяется на C++. Шаблон на момент проверки содержит Windows-предустановку генератора **Visual Studio 17 2022** и зависимости OBS **31.1.1**. Для проекта требуется зафиксировать комплект зависимостей OBS 33, убедиться в совместимости ABI/Qt и настроить собственный preset под MSVC/Ninja, если выбирается Ninja. **VS Code — редактор; Visual Studio IDE для него не требуется, но компилятор и Windows SDK необходимы.**

В расширенном окне — единая внутренняя навигация: **Потоки, Выходы, Группы кодирования, Профили, Заглушки, Диагностика, Настройки, Расширенные**. Название во всём UI — **«GOST Restreamer»**; язык реализации серверной части не выводится в пользовательских метках.

## 5. Адрес сервера и штатная трансляция OBS

На странице **«Настройки»** редактируется адрес управляющего API с кнопками
«Сохранить» и «Отмена». Ввод остаётся черновиком до сохранения; отмена возвращает
действующий адрес без подключения и записи настроек. Сохранение допустимого
нового адреса подтверждает смену сервера и начинает подключение. Тот же адрес
не перезапускает уже действующее или восстанавливаемое соединение; после
завершённого отказа его можно повторно применить кнопкой «Сохранить».

| Отображаемое поле | Пример | Назначение |
| --- | --- | --- |
| **Адрес сервера** | `http://192.168.1.100:8080` | Базовый URL API; к нему добавляется `/api/v1/...` |
| Таймаут управляющих запросов | 15 с по умолчанию; 5–60 с | Общий срок обычного REST-запроса; поле находится в «Расширенных», не распространяется на длительный SSE и загрузку файлов |

В разделе «Расширенные» задаётся число повторов подписки на события после
HTTP 400 или 409. Параметр доступен для штатного автоматического восстановления связи.
Там же задаются общий срок обычного REST-запроса и режим клиентского журнала
«Обычный»/«Подробный». В обоих режимах используется штатный журнал OBS.
Все три значения остаются черновиком до явного «Сохранить» и применяются
одним сохранением настроек. «Отмена» восстанавливает действующие значения
без записи и переподключения. Черновик переживает обновления наблюдений,
переходы между разделами и скрытие окна. Подтверждённая запись выделяется
зелёным; отказ — красным. При отказе диска новые рабочие значения остаются
в памяти согласно контракту хранилища, а повторное «Сохранить» доступно
без дополнительного редактирования.

В Dock отображается краткий статус **«Сервер подключён / Нет связи»**, текущий Stream и его фактическое состояние; адрес не дублируется отдельным полем настройки потока. Ввод `http://` или `https://` разрешён в согласованном локальном контуре; запрещены userinfo и фрагменты, TLS-ошибки не игнорируются. Удалённый доступ, авторизация и API-ключи в архитектуру плагина **не входят**.

**Трансляция OBS** настраивается только через **«OBS → Настройки → Трансляция»**: пользователь самостоятельно вводит RTMP Server и Stream Key. В текущем backend используется схема `rtmp://<server>:1935/<streamID>` и отдельный ключ Stream; в GOST Restreamer ключ **отображается в расширенном разделе «Потоки» для копирования**, но не является дополнительным полем настройки streaming service, не генерирует RTMP URL и не приводит к перезаписи настроек OBS через Frontend API.

Подключение при завершении загрузки OBS и восстановление временных отказов
выполняются штатно, без переключателей. Сохраняются паузы, предел частоты и
бюджет повторов SSE; постоянные отказы и HTTP 204 завершают восстановление.
Подключение управляющего API само по себе не запускает эфир.

Выбор Stream меняет адресата управляющих команд, но **не** меняет уже настроенный сервис OBS. Пользователь выбирает Stream в шапке Dock. На странице «Настройки» селектора потока, состояния связи и кнопок подключения/отключения нет. При смене OBS Profile плагин читает свою привязку и явно предупреждает о необходимости согласовать профиль с серверным Stream. Серверный ключ не считается автоматически введённым в OBS. Фактический ingest подтверждается только после авторизованного подключения.

Выбранный Stream запоминается отдельно для каждой пары **«сервер + OBS Profile»**. При возвращении к серверу или профилю восстанавливается выбор именно этой пары; совпадение Stream ID на разных серверах не переносит привязку между ними. **Переименование OBS Profile меняет только его отображаемое имя:** идентичность профиля и все его привязки сохраняются, повторный выбор Stream не требуется, в том числе после перезапуска OBS.

При создании Stream `POST /streams` требует `publication_key`. Плагин может сгенерировать это значение и передать серверу. **После создания, при повторном открытии «Потоков», при выборе существующего Stream и после перезапуска OBS тот же ключ должен быть доступен для просмотра и копирования.** Для Destination аналогично доступны фактические `stream_key` и полный `endpoint`, включая прежние назначения. Источник истины — серверное хранилище; одноразовая локальная копия после POST недостаточна. Контракт `103d839` предоставляет эти значения в детальных GET и списках. Право чтения в локальном контуре согласовано; маска — поведение UI карточек.

## 6. Интеграция со штатным OBS и локальная статистика

Используются официальные функции OBS Frontend API и libobs:

- `obs_frontend_add_dock_by_id()` и соответствующее удаление Dock, события lifecycle через `obs_frontend_add_event_callback()`;
- `obs_frontend_streaming_stop()`, `obs_frontend_streaming_active()`, `obs_frontend_get_streaming_output()`; запуск штатного output выполняет пользователь средствами OBS;
- чтение текущего стримингового сервиса **без изменения его RTMP-настроек**;
- FPS: `obs_get_active_fps()`; среднее время рендеринга: `obs_get_average_frame_time_ns()`;
- пропуски рендеринга: `obs_get_lagged_frames()` и `obs_get_total_frames()`;
- пропуски кодирования: `video_output_get_skipped_frames()` и `video_output_get_total_frames()` после `obs_get_video()`;
- сетевые пропуски штатной трансляции: `obs_output_get_frames_dropped()` и `obs_output_get_total_frames()` для OBS streaming output;
- переданные байты штатного выхода: `obs_output_get_total_bytes()`; текущий OBS bitrate рассчитывается по дельте байтов и фактическому времени между выборками.

Это те же классы локальных показателей, что использует штатное окно статистики OBS 33.0.1. Источник подтверждён в [OBSBasicStats.cpp (тег 33.0.1)](https://github.com/obsproject/obs-studio/blob/33.0.1/frontend/widgets/OBSBasicStats.cpp). Плагин читает данные через разрешённые API и **не** копирует/изменяет внутренние приватные структуры окна статистики OBS.

### Правила представления локальных метрик

- Пропуски показываются как **«пропущено / всего (процент)»** отдельно для **рендеринга**, **кодирования** и **сети OBS → сервер**. Это разные знаменатели и разные этапы: их нельзя суммировать.
- Наблюдаемый FPS OBS не подменяется целевым FPS настроек; среднее время рендера — миллисекунды, сетевой bitrate — бит/с, байты — MB/MiB с явным обозначением единиц.
- Отсутствующий/уничтоженный OBS output не превращается в фиктивный ноль; в состоянии «OBS не транслирует» сетевые показатели могут быть неактивны.
- `OBSStatsCollector` не управляет кодировщиками или ресурсами GPU; использование CPU/памяти OBS можно показывать в подробной диагностике **только при доступности достоверного источника**, но не требовать их для основного Dock.
- Frontend callbacks не делают синхронных HTTP-запросов; чтение и UI-обновления происходят в безопасном жизненном цикле OBS/Qt. Никакие сетевые ожидания не блокируют поток интерфейса.
- Событие `STREAMING_STARTED` подтверждает локальный OBS lifecycle, **не** успешную серверную Session и не приём потока всеми площадками.

**Стандартная кнопка «Начать трансляцию» OBS — основной запуск эфира.** В dev.7 публикация с правильным ключом запускает Session со всеми включёнными назначениями либо присоединяется к существующей по разделу 2.3. Плагин подхватывает Session выбранного Stream через REST/SSE, не отправляет второй `start` и не требует собственной квитанции для чужого запуска. В Dock кнопки «Начать эфир» нет. Серверный workflow передачи заглушки до OBS описан в разделе 10.2; его UI отложен до отдельного согласования. Остановка OBS штатной кнопкой сохраняет серверную Session и fallback-защиту.

## 7. REST API и профили кодирования

Все пути в таблице имеют префикс `/api/v1`.

| Задача | Методы |
| --- | --- |
| Сервер | `GET /health/ready`, `/health/live`, `/system/capabilities` |
| Потоки | `GET/POST /streams`; `GET/PATCH/DELETE /streams/{id}`; `GET /streams/{id}/destinations` |
| Группы и профили | CRUD `/transcode-groups`, `/transcode-profiles` |
| Назначения | CRUD `/destinations` |
| Сессии | `GET /streams/{id}/sessions`, `/sessions`, `/sessions/{id}`; `POST /streams/{id}/start`; `POST /sessions/{id}/stop`, `/pause`, `/resume` |
| Выходы Session | `GET/POST /sessions/{id}/outputs`; `GET /sessions/{id}/outputs/{outputId}`; `POST .../{outputId}/start`, `/stop`, `/detach` |
| Результат команды | `GET /commands/{commandId}` |
| Текущие метрики | `GET /sessions/{id}/metrics` |
| Заглушки | `GET/POST /fallback-assets`; `GET/DELETE /fallback-assets/{id}`; `PUT /fallback-assets/{id}/content`; `POST /fallback-assets/{id}/rebuild`; `GET /fallback-assets/{id}/generations/{generationId}`, `/fallback-assets/{id}/variants` |
| Политика заглушки | `GET/PUT /streams/{id}/fallback-policy` |
| Оперативные события | `GET /events/snapshot`; `GET /events` (SSE) |

**Команды:** `202 Accepted` означает только принятие, в теле находятся `id`, `request_id` и связанные идентификаторы. Клиент ждёт терминального `SUCCEEDED/FAILED/INTERRUPTED` через `GET /commands/{commandId}`; `PENDING/CLAIMED/ISSUED` — промежуточные состояния. Если HTTP-ответ потерян, повторяется тот же запрос с прежним `request_id`, а не новая команда. Квитанция и runtime состояние проверяются независимо.

После перезапуска плагина состояние восстанавливается чтением существующего API
по разделу 7.2; исходные POST автоматически не воспроизводятся.

**Изменения:** `expected_revision` — точное положительное JSON-число U64 в PATCH/PUT; в DELETE и других HTTP query передаётся текстом. Только `409` с `code=revision_conflict` включает сравнение исходной, пользовательской и новой серверной версии; другие `409` сохраняют предметную причину. PATCH различает отсутствие и переданные `false`/`""`/`null`; отсутствие `endpoint`/`stream_key` сохраняет значение, пустой `stream_key` очищает ключ. Идентификаторы и cursor непрозрачны; состояния Output берутся из RAM.

**Типы:** все доменные числовые поля REST/SSE и запросов — JSON-числа. Целые U64/I64 и наносекунды проходят точный лексический разбор/запись без double, с физическими и предметными границами. Математически целые записи допустимы; unsigned отвергает любой минус, включая `-0`. CRF — точные сотые с присутствием. `FFmpeg.progress.out_time_us` — nullable I64 в микросекундах. Отсутствие/`null`/ноль различимы. Даты, IDs и opaque cursor остаются строками; настройки — UTF-8 строки без Base64-оболочек. Ошибки — `application/problem+json`.

### 7.1 Актуальный редактор полных профилей dev.8

Редактор раздела «Профили» заменяет полный `profile`: `mode`, явный
`live_audio_mode`, `format`, `video_encoding`, `audio_encoding` и полный
`encoding` без поля `version`. Все настройки передаются UTF-8 строками,
без Base64-оболочек. Сохранённые и выходные профили полны. Отсутствующий/null
`encoding` допустим только как сокращение входного запроса с немедленной
материализацией серверных defaults для H.264/transcode → NVENC/VBR и
AV1/copy → SVT/CBR; прежнего видеорецепта и выбора legacy в текущем UI нет.

Основной вид сохраняет девять параметров: базовый пресет, название, обработку
видео, видеокодек, разрешение, FPS, видеобитрейт, обработку звука и аудиобитрейт.
Остальные настройки находятся в свёрнутом разделе «Расширенные настройки».
Название и основные поля используют общую колонку ввода; справочного списка
групп с техническими ID нет. Сворачивание, переходы и скрытие окна сохраняют
RAM-черновик, включая незавершённый ввод; HTTP-запись требует явного сохранения.

Битрейты вводятся точно в кбит/с: 1 кбит/с = 1000 бит/с, до тысячных.
FPS хранится исходной дробью без округления; 59,94 соответствует 60000/1001,
29,97 — 30000/1001. Справка у битрейта показывает target/max и правило CBR,
обновляется при вводе/загрузке/пресете/восстановлении и сама значения не меняет.
Чистые CQP/CRF требуют явных нулевых target/max/buffer; FLAC требует нулевого
audio bitrate. Эти нули не подменяются отсутствием или `null`.

Ровно три базовых пресета — `H.264 1080p60`, `H.264 1440p60`, `AV1 1440p60` —
сохраняют содержательные параметры профилей владельца от 14.11.2026.
Документы адаптированы к dev.8 в `tests/fixtures/backend/profile-presets.json`,
происхождение исходных параметров сохранено. H.264 использует transcode и
6000/12000 кбит/с; AV1 — copy и 10000 кбит/с для заглушки. У всех 60/1 FPS,
LIVE audio copy, AAC-тишина 160 кбит/с. Пресет применяется только явно;
новые сочетания собираются вручную, новые пресеты не добавляются.

| Блок | Контракт |
| --- | --- |
| Видео | H.264/transcode с NVENC/x264; AV1/copy с SVT/AOM; HEVC и VP9 copy/transcode с точными encoder/profile/pixel/depth зависимостями |
| Цвет | Поддержанная SDR-матрица; HDR PQ/HLG только в применимых 10-bit BT.2020/BT.2020nc сочетаниях, без выдуманного tone mapping |
| LIVE audio | Явные copy/transcode; audio transcode требует video transcode, FLAC требует оба transcode |
| Аудиоформат | AAC LC с точными sample-rate/layout/channel/bitrate связями; Opus/FLAC/MP3/AC-3 с фиксированными 48 kHz stereo привязками |
| Rate control | CBR/VBR и применимые CQP/CRF; `qp` — целое, `crf` — точные сотые с отдельным присутствием, включая ноль |
| NVENC/SVT | Только применимые полные блоки, конечные настройки и пределы выбранного кодировщика; неприменимый блок запрещён даже пустым |
| Custom | Отдельные контролы разрешённых `nonref_p`, `strict_gop`, `lp`, `aac_coder`; произвольная CLI и raw JSON UI отсутствуют |

Один чистый модуль правил задаёт допустимые списки, применимость и проверку
полного профиля. Каталог следует закреплённым исходникам dev.8, а не объединению
всех enum. Учитываются точные FPS/time-scale ограничения, H.264 6.x budgets и
применимый SVT high-tier tile layout. Наличие executable в capabilities не
подтверждает аппаратную исполнимость каждого сочетания.

Конечные параметры выбираются из нередактируемых списков; числовые диапазоны —
типизированным вводом. Смена определяющего поля пересчитывает зависимые списки.
Несовместимое исходное значение остаётся видимым отдельным недоступным пунктом,
без молчаливой замены. Полная замена блокируется до явного исправления.
Неизвестный исходный документ и его проекция сохраняются в RAM; переименование
отправляет только имя и ревизию. Новый профиль не наследует неизвестные значения.
Неактивный ввод сохраняется в черновике, но неприменимые quality/encoder поля
в исходящий профиль не попадают.

Полное равенство desired-рецептов включает все параметры, присутствие QP/CRF,
аудиорежим, битрейты, custom и настройки encoder; FPS сравнивается математически.
Совместимость `Variant.format` проверяется отдельно по серверному правилу:
математический FPS; range tv/pc → limited/full; только transfer bt470m/bt470bg
→ gamma22/gamma28; пустой/auto desired level и пустой tier не ограничивают
соответствующее измерение. Остальные видео- и аудиополя совпадают точно.
Нули/пустота/UNKNOWN допустимы при чтении измерения, но не являются общим wildcard
и не становятся desired-настройкой. READY и совпадение геометрии недостаточны.

Изменение полного профиля действует на следующий запуск/новое прикрепление,
сохраняя снимок текущего Output. Для будущего эфира нужен подходящий подготовленный
fallback-вариант полного рецепта. Звук исходного видео заглушки не сохраняется:
готовится цифровая тишина выбранной аудиопривязки. LIVE copy требует фактической
совместимости с ожидаемым форматом; автоматического transcode при отказе нет.

Контрактная база: pinned dev.8 `252669d054401f8c6081be49521f1c7f44410bec`,
[числа](https://github.com/GregoryGost/gost-restreamer/blob/252669d054401f8c6081be49521f1c7f44410bec/docs/numeric-json-contracts.md),
[строки и матрица](https://github.com/GregoryGost/gost-restreamer/blob/252669d054401f8c6081be49521f1c7f44410bec/docs/string-json-contracts.md).
OpenAPI экспортирован в Git ревизии `95f5245`, добавляющей только файлы схемы
к тем же исходникам. Это не подтверждает установленную сборку или live-приёмку.

### 7.2 Восстановление состояния после перезапуска OBS

Восстановление использует существующий REST/SSE API и не требует изменений
backend. Плагин заново определяет точную Session выбранного Stream, перечитывает
её состояние, паузу, состав выходов и доступные runtime-наблюдения, затем
продолжает показывать фактический эфир. Работающая серверная Session может
передавать заглушку при остановленной OBS; это самостоятельные состояния.

Результат прежней команды и текущее состояние сервера — разные факты.
В живом workflow плагин хранит в RAM исходные параметры, `request_id` и полученный
`command_id`; квитанция читается через существующий `GET /commands/{commandId}`.
Повтор потерянного запроса использует прежний `request_id` и те же параметры.
Если после перезапуска идентификатор квитанции недоступен, результат прежней
команды остаётся неизвестным. Это не мешает показать подтверждённое текущее
состояние, но не позволяет объявить прежнюю команду успешной.

После перезапуска плагин не воспроизводит старые POST и не продолжает
неотправленные шаги пакетов, включая следующий `start` в `stop → start`.
Новые действия выполняются только по новому явному намерению пользователя
и после проверки текущего состояния. Подхват существующего эфира сохраняет
паузу и намерения выходов; смена Session не переносит в неё прежние операции.
Отдельный журнал команд на диске и серверный поиск по `request_id` для T04
не требуются. Недоступное или неполное чтение остаётся неизвестностью.

## 8. SSE, снимки и мониторинг

Алгоритм `EventClient`:

1. Получить `GET /events/snapshot` с массивом runtime-сессий, GPU и непрозрачным `cursor`.
2. Установить снимок в `StateStore` и открыть `GET /events?cursor=<cursor>` с `Accept: text/event-stream`.
3. Инкрементально разбирать SSE-фреймы (`event`, `id`, многострочное `data`, комментарии-heartbeat) с корректной обработкой частичных TCP/UTF-8 чанков.
4. Применять события только к соответствующим идентичностям Session/Output/Group и непротиворечивой ревизии наблюдения, не смешивать предыдущий runtime epoch с новым.
5. После обрыва пробовать восстановление с последним подтверждённым cursor (`Last-Event-ID` **либо** query cursor, не с противоречивыми значениями).
6. При `resync_required`, потере epoch/событий, несовместимом payload либо недостоверном восстановлении повторить snapshot→subscription.
7. Поддерживать bounded frame buffer, ограниченное число повторов за короткий промежуток, backoff с jitter и отмену запросов при закрытии OBS/смене сервера.

Подключение подтверждается при `200` с `Content-Type: text/event-stream`.
До получения заголовков UI показывает подключение или восстановление.
Подтверждение происходит и при отсутствии событий с данными. Незавершённый
кадр при обрыве отбрасывается, восстановление использует подтверждённый курсор.

`GET /sessions/{id}/metrics` используется для детального текущего снимка по конкретной сессии; результаты команд читаются отдельно из долговечных квитанций. Снимок RAM и история SQLite не атомарны относительно друг друга: `StateStore` должен корректно показывать краткие переходные состояния.

Показатели UI (каждый источник независим):

- OBS: статус собственного streaming output; локальные FPS, среднее время рендеринга, пропуски рендеринга/кодирования/сети, локальный bitrate и отправленные байты (см. раздел 6).
- Вход рестримера: авторизованный `connected`, фактически определённые codec, resolution, FPS, время последнего кадра и измеренный bitrate.
- Session: сохранённое `STARTING`, `RUNNING`, `STOPPING`, `STOPPED`, `FAILED`, `INTERRUPTED`, отдельный флаг `desired_paused`, текущая доступность оперативных данных.
- Groups: источник `LIVE`, `FALLBACK` или отсутствие наблюдения, формат и общие показатели группы.
- Outputs: `CONNECTING`, `PUBLISHING`, `RETRYING`, `FAILED`, `STOPPED`; попытки, очереди, отправленные байты, FPS/bitrate, потери очереди и доставки по отдельным категориям; опережающие RTMP ACK только в подробной диагностике (не классифицировать как потери).
- FFmpeg: статус попытки, progress, fps/speed/drops при наличии.
- GPU: `utilization`, `encoder_utilization`, `decoder_utilization`, VRAM и **отдельная доступность каждой метрики**.

Доступность измерений обозначается подписями из раздела 11.3. Нулевое значение отображается только при наличии измерения с таким значением. `PUBLISHING` не гарантирует успешное воспроизведение на YouTube/VK: T11 отдельно подтверждала изображение и звук владельцем на конкретных площадках, но такого подтверждения нет в публичных полях REST/SSE. Серверный NVENC/NVDEC — метрики **GPU сервера**, а не видеокарты игрового ПК.

### 8.1. Дополнительная диагностика RTMP ACK (контракт Go от 08.11.2026)

Go backend публикует четыре поля непосредственно в `OutputMetricsDTO`, **не** в `metrics.counters`. Они доступны в `GET /sessions/{id}/metrics` (`snapshot.outputs[].metrics`), детальном `GET /sessions/{id}/outputs/{outputId}` (`runtime.metrics`, если наблюдение доступно) и в payload выходных событий SSE (`output`). Плагин отображает их в **DiagnosticsView → конкретный Output → RTMP ACK**, не перегружая основной Dock.

| Поле | Представление API | Отображение |
| --- | --- | --- |
| `ack_ahead_events_total` | JSON-число `uint64` | Количество достоверно измеренных опережающих подтверждений за текущий запуск Output |
| `ack_ahead_bytes_last` | JSON-число `uint64` | Размер последнего измеренного опережения, RTMP-байты |
| `ack_ahead_bytes_max` | JSON-число `uint64` | Максимальное измеренное опережение за запуск Output, RTMP-байты |
| `ack_last_anomaly_at` | UTC timestamp либо `null` | Время последнего измеренного события либо «не наблюдалось» |

**Семантика:** учитываются только ACK, для которых локальный RTMP-транспорт достоверно измерил опережение. Нормальные, повторные и неоднозначные ACK не создают событий. Во время физического `Write` и после потери однозначной эпохи счётчика некоторые случаи не измеряются; следовательно, `0` **не доказывает отсутствие расхождений**. Сами ACK-поля не измеряют пропажу видеокадров, TCP retransmits, задержку сети и факт воспроизведения на площадке; не менять статус Output и не запускать автоматические действия на их основании.

**Жизненный цикл:** счётчики и значения last/max сохраняются при RTMP reconnect **того же** Publisher/запуска Output; на новом запуске Output начальные числа равны `0`, время `null`. Завершение Session и перезапуск backend не восстанавливают эту телеметрию из SQLite. Обычные ACK не обнуляют последнее значение, максимум или время. Насыщение счётчиков отражается существующим общим `metrics.media.saturated`, без переполнения с возвратом к нулю; этот флаг сам по себе не указывает, какой именно счётчик насыщен. Если `metrics`/`runtime` отсутствует, UI показывает «нет данных», а не нули.

**Обновление клиента:** первоначально переданный для плагина `openapi.yaml` этих полей не содержал; на 08.11.2026 они присутствуют в `internal/api/runtime_dto.go` и контракте Go. Для dev.8 поля сверены с опубликованной в Git OpenAPI ревизии `95f5245`, добавляющей схему к тем же исходникам `252669d`. Происхождение зафиксировано в fixture; фактическая установленная сборка отдельно не подтверждена. Воспроизводить параметры по старому YAML нельзя. Новых API-маршрутов, опросчиков, постоянного хранилища метрик или отдельных SSE-подписок плагину не требуется.

### 8.2. Контракт состояния клиента

REST configuration/history/detail и авторитетные runtime-наблюдения хранятся
раздельно. `Session.stream/groups` и `Output.destination/group/profile/fallback`
владеют историческими снимками по значению; поздний REST-ответ не откатывает SSE.
Один установленный anchor и одна последовательная подписка задают runtime.
Непрозрачный cursor подтверждается после применения события и не сортируется.

Неполное повторное чтение состава выходов той же Session обновляет полученные
записи и сохраняет ранее известные элементы, отсутствующие в полученной части.
Полный список заменяет сохранённые REST-метаданные; явно полученный
`attached=false` учитывается и в неполном ответе. Независимо наблюдаемое
runtime-исполнение продолжает отображаться по своему состоянию, пока нет
подтверждённого отсоединения; отсутствие его REST-метаданных не позволяет
считать сводку состава полной. При смене Session
или тройки «сервер + UUID профиля OBS + Stream» прежний состав не переносится.
Сводка «N из M транслируют» требует полного состава и подтверждённых состояний.

Отдельный каталог назначений выбранного Stream загружается для Dock независимо
от наличия Session и открытия редакторов. Проекция содержит только ID и имя,
включает отключённые для следующего эфира назначения и не хранит endpoint/key.
Полный ответ заменяет каталог, частичный обновляет известные записи без удаления
пропущенных; отказ и потеря связи сохраняют строки как устаревшие. Контекст
сервера/UUID/Stream очищает каталог, смена Session его не очищает. Ответы
ограждены контекстом, поколением чтения и поколением конфигурации; инвалидация
отзывает старое чтение и сохраняет запрос актуального перечитывания.

Строки текущих Outputs сохраняют точные Session ID/Output ID и имя закреплённого
снимка. Каталог добавляет строку назначения, если его ID ещё не представлен
прикреплённым Output. Несколько Outputs одного назначения остаются отдельными
строками; runtime без доказанной REST-связи не объединяется по имени. После
серверного detach сохранённое назначение остаётся в списке без прежнего исполнения.
Пакетные команды фиксируют именно показанную проекцию, включая каталоговые
и неопределённые строки, до подтверждения; новые строки не добавляются.
Недоказанная адресация получает отдельный NotSent вместо скрытого пропуска.
Каталоговые строки не входят в знаменатель текущих Outputs: при дополнительных
каталоговых или неопределённых строках сводка N/M скрыта. Каталоговые команды
требуют полного свежего чтения; исторические attached-цели сохраняют собственные снимки.

Ревизии state и metrics независимы. Anchor не сообщает metrics watermark;
первое последующее измерение принимается независимо от state revision. Input
lifecycle с revision=0 сбрасывает входную телеметрию; attempt сбрасывает метрики
и наблюдение соответствующего FFmpeg. Идентичность учитывает actual instance:
одна конфигурационная Group и одна роль FFmpeg могут иметь несколько наблюдений.
Удаление затрагивает точную identity и её потомков, сохраняя новое исполнение
Output. Неизвестный родитель FFmpeg допускает временную группу с известным
instance ID; противоречивая иерархия требует нового anchor.

## 9. Состояния и оперативные действия на дашборде

### 9.1 Независимые состояния

| Ось | Источник истины | Наблюдаемые значения |
| --- | --- | --- |
| Штатный OBS streaming output | OBS Frontend/libobs | Не запущен, запускается, передаёт, останавливается |
| Подключение API | HTTP/SSE клиент | Подключено, переподключение, нет связи |
| Вход рестримера | `RuntimeSessionDTO.input.connected` | LIVE принимается / источник отсутствует |
| Session | `SessionDTO.state` | `STARTING/RUNNING/STOPPING/STOPPED/FAILED/INTERRUPTED` |
| Желаемая пауза | `SessionDTO.desired_paused` | Пауза включена/выключена |
| Фактический источник группы | runtime `groups[].source` | `LIVE/FALLBACK/NONE` |
| Выход | `RuntimeOutputDTO` + `OutputDTO` | `CONNECTING/PUBLISHING/RETRYING/FAILED/STOPPED`, attached и desired_running |
| Команда | `ReceiptDTO` | `PENDING/CLAIMED/ISSUED/SUCCEEDED/FAILED/INTERRUPTED` |

При частичном отказе Dock показывает «2 из 3 транслируют» независимо от состояния Session. Фактический `LIVE/FALLBACK` принадлежит каждой группе. При смешанном состоянии Dock показывает «Прямой эфир 2 · Заглушка 1» или «Live input 2 · Fallback 1» в зависимости от языка интерфейса. После T15 одной из причин продолжения `FALLBACK` может быть несовместимый формат копируемого LIVE AAC; плагин **не угадывает причину** по одному `source=FALLBACK`, поскольку детальная причина находится в серверном журнале. `PUBLISHING` не доказывает воспроизведение видео у зрителей; локальный `OBS STREAMING_STARTED` не доказывает авторизованный ingest.

### 9.2 Действия с эфиром

- **Обычный запуск** — штатная кнопка OBS. Созданная сервером Session подхватывается через REST/SSE; команды запуска выходов в Dock не включают OBS.
- **«Запустить заглушку»** — предусмотренный серверный workflow: запустить только Session и дождаться собственной квитанции `SUCCEEDED` и `RUNNING`. Штатный output OBS не включается. Размещение действия в UI будет согласовано при реализации заглушек; в редакторах конфигурации его нет.
- **«Пауза / Возобновить»** — только серверные команды `pause/resume` для точной Session; OBS продолжает транслировать. Переход LIVE/FALLBACK подтверждается наблюдением групп.
- **«Завершить эфир»** — сначала остановить OBS output, включая его переподключение, затем точную Session. Обе операции отслеживаются отдельно; неподтверждённая остановка OBS оставляет частичный/неизвестный результат даже при успешном серверном stop, поскольку новая публикация может начать следующий эфир.
- Остановка OBS обычной кнопкой **не** эквивалентна завершению Session: сервер может продолжать отдавать fallback.

### 9.3 Отдельный выход и массовые операции

Backend предоставляет **только отдельные** `start`, `stop`, `detach` для текущего Output и `add-output` для нового присоединения. Механизма `restart` или массовой операции через один API-запрос нет.

| Кнопка Dock | Последовательность действий плагина |
| --- | --- |
| «Запустить» у выхода | В RUNNING Session для прикреплённого остановленного Output — `POST .../start` после проверки `attached=true`, `desired_running=false`; для назначения без прикреплённого Output — `add-output` в точную Session. При подтверждённом отсутствии активной Session — `POST /streams/{id}/start` с единственным выбранным `destination_id` после проверки его заглушки. OBS и соседние назначения не запускаются, `enabled` не меняется |
| «Остановить» у выхода | `POST .../stop` для выбранного `output_id` |
| «Перезапустить» у выхода | `stop` → квитанция и проверка состояния → `start` с **новым** `request_id`, не создавая новую Session |
| «Подробности» у выхода | Открыть настройки точного Destination в прежнем расширенном окне независимо от Session/запуска, сохраняя черновики и маски |
| «Запустить все» | Зафиксировать показанные строки. Attached desired=true не прерывать, desired=false запустить; каталоговые присоединить к исходной RUNNING Session. При отсутствии Session первая пригодная строка создаёт собственную singleton Session, остальные добавляются в неё |
| «Остановить все» | С подтверждением выполнить output-stop для показанных attached Outputs; каталоговые без исполнения — явный no-op. OBS и Session сохраняются |
| «Перезапустить все» | С подтверждением выполнить stop → собственная квитанция/оракул → start точного attached Output, включая первоначально остановленный. Каталоговые запустить как в «Запустить все» |

Перед массовой операцией фиксируются context, исходный Session ID/режим, поколение конфигурации и весь показанный список с раздельными Destination/Output IDs, включая строки за прокруткой. Набор берётся из отображённой модели, а не перечитывается из server.outputs/каталога; новые строки после подтверждения не добавляются. Неподтверждённая строка получает честный NotSent. Для каждого шага — собственный request_id, квитанция и долговечный оракул. Один RestreamController последовательно выполняет строки, не вызывая из UI цепочку самостоятельных workflows.

Определённый отказ или локальный Unknown одной строки сохраняет её результат и пропускает её зависимый остаток. Остальные независимые строки продолжаются только после подтверждения той же RUNNING Session при непрерывно пригодной связи. Неизвестный stop не разрешает start этой строки. Потеря общей Session/контекста/связи закрывает новые действия без автоматического продолжения при восстановлении. До Session определённый отказ precheck позволяет рассмотреть следующую исходную цель; отправленный bootstrap409/Unknown/отказ собственной Session прекращает остаток без усыновления чужой Session. Собственная Session доказывается receipt+точным GET отдельно от результата первого Output, без ожидания обновления observer cache.

Внутри одного workflow каждому активному шагу назначается отдельный token, инвалидируемый до cancel/замены live: запоздалый ответ прежней строки не меняет следующую. Не более одного неизвестного шага на строку хранится в ограниченной RAM с прежними action/IDs/payload/request/command/receipt/pin. Существующая Retry выбирает первый Unknown по исходному порядку, показывает имя цели и повторяет только этот шаг. Повтор stop не отправляет пропущенный start и не объявляет restart завершённым; восстановление bootstrap не возобновляет add остаток. Последний успех не подменяет результаты остальных строк. Общий Completed требует подтверждения всех необходимых частей либо явного no-op, отдельно от PUBLISHING.

Индивидуальный запуск фиксирует context, Destination ID, Output ID при наличии и одну из трёх ветвей до открытия меню. После вложенного цикла событий цель проверяется повторно; появление другой Session не превращает создание в add-output. Каталоговые ветви требуют полного свежего каталога, добавление в RUNNING — также полного свежего состава Outputs. STARTING/STOPPING и неполные либо устаревшие наблюдения не разрешают новую команду. Исторический Output завершённой Session не используется для нового запуска.

При создании Session приватная предварительная проверка относится только к выбранному Destination и текущему поколению завершённой конфигурации: проверяются Stream, Group/Profile, policy, Asset, точное current Generation и все его variants по правилам раздела 10.7. Явный выбор допускает `enabled=false`; неподготовленный сосед не блокирует выбранное назначение. Публичная проверка всех Enabled сохраняет прежний смысл. Перед первым POST заново подтверждается отсутствие STARTING/RUNNING/STOPPING; `destination_ids` содержит ровно выбранный ID. Конфликт409 или чужая Session завершают попытку без автоматического add, rollback и принятия чужого успеха.

Успех собственного создания требует собственной квитанции `start_session` SUCCEEDED, точной RUNNING Session из неё и подтверждённого выбранного Output. Полное чтение Outputs этой Session должно найти единственную запись выбранного Destination с учётом отсоединённой истории; затем закреплённый Output ID проверяется адресным GET, включая принадлежность Stream/Session/Destination, внутреннюю согласованность снимков, `attached=true` и `desired_running=true`. Неоднозначный состав не позволяет выбрать первый или новейший Output. Это подтверждает исполнение команды, но не PUBLISHING или воспроизведение у зрителей. Потерянный ответ повторяется только явно, с теми же `request_id`, payload и целью; уже отправленный запрос не требует нового доказательства отсутствия Session.

`RETRYING` — автоматическая серверная попытка переподключения, а не команда, которую плагин должен вызывать повторно. Если Output уже имеет `desired_running=true`, нельзя отправлять `start` вслепую: возможен `409`. `FAILED` анализируется по долговечному состоянию и актуальному желаемому запуску; при необходимости используется контролируемое `stop→start`. Backend поддерживает отдельный detach, но меню Dock и редактор конфигурации его не предлагают. Изменение `Destination.enabled` меняет будущие запуски, но не заменяет текущие output-команды.

### 9.4 Сброс отображаемой статистики

Кнопка **«Сбросить отображаемые счётчики»** работает **только на стороне клиента**: `StatsBaseline` запоминает исходные накопительные счётчики OBS и Go. Видимое значение за выбранный интервал = текущий счётчик минус исходный (если совпадают идентичность источника и эпоха счётчика); вычисление процентов использует соответствующий знаменатель **за тот же интервал**.

- Текущие FPS, bitrate, время рендера, состояния и показатели загрузки GPU **не обнуляются**: это мгновенные/оконные значения.
- Счётчики серверных `queue_drops` и `delivery_drops` не становятся «пропущенными кадрами сети»; выводить их отдельно с ясным названием.
- При новой OBS streaming-сессии, новом Output execution/generation, рестарте сервера, смене `source_epoch`, регрессе или насыщении значения baseline переустанавливаются по проверенной идентичности; отрицательной статистики не бывает.
- ACK `ack_ahead_bytes_last/max` и время последней аномалии — **не накопительные величины**, к ним вычитание baseline не применяется. Для числа ACK-событий допустим счёт «с момента сброса» только при той же идентичности исполнения. Полные необнулённые значения доступны в диагностике.
- Серверного API для очистки счётчиков нет; кнопка не вызывает перезапуск Output/Session и не изменяет DB или libobs counters.

Видимая статистика OBS в Dock содержит числовые значения без подписей периода («С момента сброса»/«Текущий запуск»), в том числе после локального сброса и при разных эпохах источников. Внутренние периоды и правила расчёта дельт сохраняются. Ключ трансляции серверного Stream показывается и копируется только в расширенном разделе «Потоки», не в Dock; значение читается из существующего GET Stream и не передаёт плагину управление RTMP-настройками OBS.

## 10. Основные сценарии

### 10.1 Первый запуск / привязка

1. Плагин добавляет Dock и регистрирует callbacks после завершения загрузки OBS.
2. Пользователь вводит `Backend API URL`, выполняется `GET /health/ready`.
3. Получаются список Streams и необходимые страницы связанных сущностей.
4. Пользователь выбирает серверный Stream. В расширенной странице «Потоки» отображается его постоянный ключ публикации и кнопка **«Копировать»**; при создании нового Stream ключ формируется и сразу показывается. После закрытия и повторного открытия страницы ключ должен читаться из backend и оставаться доступным. В компактном Dock ключ не отображается.
5. Пользователь настраивает **OBS → Настройки → Трансляция** стандартным способом. Плагин не запрашивает ingest-адрес и не меняет текущий streaming service.
6. Плагин проверяет доступность управляющего API и выбранный Stream, при необходимости предупреждает о неактивной или отсутствующей штатной конфигурации OBS. Читаемый ключ Stream показывается как справочное значение для вставки в OBS; подтверждать совпадение сохранённого в OBS ключа и серверного ключа по одному лишь выбору Stream нельзя. Успешный ingest устанавливается фактической авторизованной публикацией.
7. Привязка выбранного Stream хранится отдельно для пары «сервер + текущий OBS Profile» только как предпочтение пульта; она не изменяет настройки OBS. Возвращение к этой паре восстанавливает её выбор. Переименование профиля сохраняет его привязки к серверам без повторного выбора Stream.

### 10.2 Запуск через OBS и предварительный запуск заглушки

**Обычный эфир:** пользователь нажимает штатную кнопку OBS. Сервер проверяет ключ, при необходимости создаёт Session со всеми включёнными назначениями и ждёт локальной готовности перед допуском входа. Плагин не перехватывает эту кнопку, не отправляет дополнительный REST start и не запускает OBS сам. Предварительная пригодность заглушки по разделу 10.7 доступна пользователю до эфира, но не подменяет серверный допуск.

Плагин обнаруживает активную Session выбранного Stream как при начальном snapshot, так и при её появлении после подписки. Принадлежность подтверждается REST-данными; локальный OBS event сам по себе её не доказывает. Подхват `STARTING/RUNNING` сохраняет ручную паузу и состояние выходов, без скрытых `start/resume/add-output`. Собственная квитанция плагина для такого запуска не требуется; Session, ingest и площадки отображаются по независимым наблюдениям. Неизвестность чтения не считается отсутствием Session. Смена Session прекращает новые шаги прежних операций и не переносит их в новый эфир.

**Предварительная заглушка:** описанный ниже серверный workflow сохраняется. Проверка и запуск не размещаются в редакторах «Потоки» и «Выходы»; интерфейс будет отдельно согласован при реализации управления заглушками.

**Отдельный выход без OBS:** пользователь выбирает «Запустить» в меню строки Dock. Плагин выполняет одну из трёх ветвей раздела 9.3, при необходимости создавая серверную Session только для выбранного назначения с уже подготовленной заглушкой. Отдельного ручного создания Session и новой панели проверки не требуется. Существующая проверка всех включённых назначений не подменяется результатом этой приватной проверки.

1. Проверить API, выбранный Stream, подтверждённое отсутствие активной Session и предварительную пригодность уже подготовленной заглушки по разделу 10.7. Неполное или недоступное чтение не разрешает слепой start. При существующей `STARTING/RUNNING` подхватить её; при `STOPPING` показать завершение без нового запуска.
2. Отправить `POST /streams/{id}/start` с **одним сохраняемым в RAM workflow** `request_id` и непустым явно зафиксированным `destination_ids`. До действия пользователь видит эти назначения. При пустом наборе показать «Нет включённых назначений» без POST: отсутствие/пустой список на сервере означает динамический выбор всех включённых и не фиксирует показанный состав.
3. Получить `202` и `Location`, дождаться собственной терминальной квитанции `SUCCEEDED` и точной Session `RUNNING`. При `FAILED/INTERRUPTED` показать отказ. Потерянный ответ восстанавливать с тем же `request_id`; при конфликте с параллельной публикацией OBS перечитать Session и не создавать новое намерение запуска вслепую.
4. Показать передачу заглушки по фактическим observations групп и выходов. OBS не включается; когда пользователь запустит её штатной кнопкой, сервер присоединит вход к этой Session с сохранением её паузы и состояния выходов.

При ошибке или таймауте подключения OBS после принятого сервером запуска Session может остаться `RUNNING` с fallback. Перечитать состояние, показать продолжающийся эфир и доступное явное завершение; не выполнять скрытый stop или повторный start.

**Граница успеха:** HTTP `202` подтверждает принятие собственной команды; её исполнение требует квитанции и состояния. Для серверного автозапуска используются наблюдения Session без выдуманной клиентской квитанции. `Generation ready` не равна готовности fallback-дорожки; `Session RUNNING` не равна принятому ingest; `OBS STREAMING_STARTED` не подтверждает публикацию на каждой площадке.

### 10.3 «Пауза» и «Возобновить»

Плагин отправляет одну команду на точную Session, ждёт результат квитанции, показывает промежуточный статус до фактического перехода групп `LIVE↔FALLBACK`. Штатную трансляцию OBS не останавливает. При `Resume` без подключённого OBS сервис может продолжать показывать fallback — это корректное состояние, а не признак успешного возврата LIVE.

### 10.4 «Завершить всё»

1. Зафиксировать намерение завершить конкретную Session; заблокировать повторное несогласованное действие.
2. Остановить штатный OBS streaming output, включая цикл переподключения, и подтвердить его остановку. Если OBS уже остановлена, не запускать её. Ошибка или истечение ограниченного ожидания остаются отдельным неподтверждённым результатом.
3. Передать `POST /sessions/{id}/stop` с сохраняемым `request_id` для зафиксированной Session. Если остановка OBS не подтверждена, серверный stop остаётся отдельно отслеживаемой частью намерения; показать предупреждение о возможном новом эфире при следующей публикации, не скрывая частичный итог.
4. Дождаться терминальной квитанции и конечного состояния Session. При потере сети — показывать **неизвестный итог**, восстанавливать квитанцию и не выдавать «остановлено» без подтверждения.
5. Если OBS остановилась, а Go Session осталась `RUNNING`, явно показать продолжающуюся серверную трансляцию/fallback и предложить безопасный повтор остановки.
6. Общий успех требует подтверждённой остановки OBS и завершения точной Session. Если уже обнаружена новая Session, показать её как отдельный эфир; не объявлять «всё завершено», не переносить старый stop на неё и не начинать бесконечную цепочку остановок.

### 10.5 Обрыв OBS / восстановление

При исчезновении медиапотока сервер удерживает Session и переводит группы на fallback по watchdog. Плагин показывает раздельные реальные состояния `OBS: не передаёт` + `Session: RUNNING` + `Group: FALLBACK` + `Output: PUBLISHING` (когда они действительно наблюдаются); не вызывает автоматически `stop`. Повторная публикация присоединяется к активной Session, сохраняя паузу и остановленные/отсоединённые выходы. Если активной Session уже нет, новая публикация в dev.7 может создать следующий эфир; плагин обнаруживает его с новой идентичностью и не переносит прежние команды или счётчики. **Переход в FALLBACK с сохранением трёх исходящих соединений наблюдался в T11 после штатной остановки OBS**. Автозапуск и `Publisher Override` dev.7 требуют отдельной Windows/OBS-проверки; плагин сам не создаёт Session/Outputs по событию восстановления входа.

### 10.6 Перезапуск сервера или плагина

- **Плагин перезапущен, сервер работает:** получить заново Streams, активную/сохранённую Session, snapshot и SSE; восстановить фактическое состояние по разделу 7.2; сопоставить с текущим OBS Profile. Неизвестный результат прежней команды не подменять успехом. Не продолжать неотправленные шаги пакетов и не выполнять `Start` автоматически.
- **Go backend перезапущен:** старая медиасессия сама не возобновляется. Новая публикация, в том числе автоматическое переподключение OBS, может создать новую Session без отдельного действия в плагине. Восстановить snapshot/SSE, перечитать активную Session выбранного Stream и отобразить новую идентичность; прежние операции/счётчики не переносить. Если OBS остановлена и публикации нет, одно восстановление API новый эфир не запускает.
- **Переподключение SSE:** не менять серверную Session, не сбрасывать OBS, восстановить поток событий или новый snapshot.
- **Обычная кнопка Start/Stop OBS:** Start является основным путём запуска dev.7 по разделу 10.2; Stop прекращает источник, сохраняя Session и fallback. Плагин не дублирует Start и не превращает Stop в `Stop All`.

### 10.7 Подготовка и проверка готовности заглушек

Плагин предоставляет два **разных** признака: **«файл подготовлен по данным API»** и **«серверная Session готова к эфиру»**. Первый определяется чтением сохранённых данных, второй — фактическим состоянием Session и дополнительно результатом команды при собственном предварительном запуске. `GET /health/ready` не проверяет пригодность заглушек: это готовность управляющего HTTP API.

**Проверка выбранного Stream до эфира:**

1. Через `GET /streams/{id}/fallback-policy` определить назначенный `asset_id`. Отсутствующая политика отображается как «Заглушка не назначена».
2. Через `GET /fallback-assets/{assetId}` прочитать `current_generation_id`, `pending_generation_id`, `state`. Если current отсутствует, рабочее поколение не подтверждено; pending отображается как отдельное задание.
3. Для **точного** current запросить `GET /fallback-assets/{assetId}/generations/{currentId}` и убедиться, что его `status == ready`. Значения `queued/preparing/error` у pending не заменяют статус current и не делают его автоматически непригодным.
4. Получить **все страницы** `GET /fallback-assets/{assetId}/variants?generation_id={currentId}`. Показать состояния каждого варианта (`READY/PREPARING/FAILED`), формат и структурированный профиль. Сопоставить опубликованные профили с группами выбранного Stream через `/transcode-groups` и `/transcode-profiles`, включая фактически выбранные назначения. Если для нужного профиля нет соответствующего READY-варианта, показать «Требуется повторная подготовка».
5. Совпадение видимых профилей и `ready` является **предварительным** выводом. Публичный `VariantDTO` не содержит `profile_key`, `generator_version`, checksum/путь файла; плагин не может самостоятельно доказать точное совпадение внутренней identity, физическую целостность и готовность проигрывателя. Не выводить «Гарантированно готов к эфиру» на основании одних метаданных.
6. Окончательную проверку выполняет сервер при запуске Session через API или публикацию OBS: проверяет опубликованное поколение, точные профили/варианты и файлы, затем фактическую готовность fallback-дорожек. Для собственного предварительного запуска плагин ждёт `GET /commands/{id}` и `Session RUNNING`; при обычном запуске наблюдает Session и допущенный ingest. Сам плагин OBS не запускает.

**Создание и замена:** плагин создаёт Asset (`POST /fallback-assets`) либо выбирает существующий, передаёт `PUT /fallback-assets/{id}/content?kind=image|video&expected_revision=...` с `Content-Type: application/octet-stream`, сохраняет `generation_id` из ответа `202` и опрашивает `GET /fallback-assets/{id}/generations/{generationId}` до `ready` или `error`. При `rebuild` используется `POST /fallback-assets/{id}/rebuild` с `expected_revision`; повторной загрузки файла не требуется. В интерфейсе есть отдельная кнопка «Подготовить заново». Процент серверного кодирования не выдумывается, отображается лишь известный прогресс отправки файла.

**T15 — звук заглушки и обязательная переподготовка после обновления:** даже если загружен ролик с аудио, серверный вариант содержит цифровую тишину выбранной поддержанной аудиопривязки; AAC-тишина относится к AAC-профилю. В интерфейсе у выбранного Asset явно написано: «Звук исходного видео не используется. Подготовленный fallback беззвучен». Нельзя предлагать настройку «сохранить звук исходного видео» или отдельный клиентский способ отключить тишину. Для перехода с генератора до `fallback-fmp4-silent-v2` требуется `rebuild` каждого используемого Asset **до** запуска эфира. Старый `current`/`READY` остаётся виден в истории, но не пригоден к воспроизведению новым сервером; при неудаче подготовки он не становится пригодным. `VariantDTO` не содержит версии генератора, поэтому UI не объявляет такой комплект совместимым только по `READY`. Информацию о необходимости rebuild после обновления выводить в соответствующем разделе и в справке перед запуском; автоматическое определение версии генератора из неподдерживаемого API не закладывается. Новые варианты не подменяют старые закреплённые OutputSnapshot. Возможный короткий остаток LIVE-звука у получателя непосредственно при переключении не считается звуком файла заглушки.

**Замена без потери рабочего поколения:** если у Asset есть и `current_generation_id`, и `pending_generation_id`, показывать два статуса («Используется текущее» и «Готовится новое»). Ошибка pending не означает отказ уже опубликованного current. После окончания задания перечитать Asset: только сервер определяет новое current. Изменение групп/профилей после подготовки может сделать текущие варианты несовместимыми; UI повторяет предварительную проверку после таких изменений и предлагает `rebuild` при необходимости.

**Ограничения:** backend не разрешает upload/rebuild при активной Session, включая ручную паузу. Плагин заранее отображает это ограничение, но решение о допуске остаётся серверным; `409` не обходится. Потеря HTTP-соединения во время подготовки не доказывает отмену серверной задачи: после восстановления проверить точное поколение и Asset, не запускать новое задание вслепую.

### 10.8 Массовый перезапуск и сброс статистики

Последовательности «Запустить все», «Остановить все» и «Перезапустить все» описаны в разделе 9.3: состав ограничен показанной моделью, включая каталоговые строки, и результат хранится для каждой исходной строки. Первая пригодная цель при отсутствии Session создаёт собственный серверный сеанс, остальные используют его. Остановка/запуск при restart — отдельные долговечные команды с собственными request_id/квитанциями; остановленные выходы также запускаются. Локальный отказ не прекращает независимые строки при доказанном общем контексте. Общая неизвестность прекращает остаток, ручной повтор не возобновляет его. «Остановить все» сохраняет OBS и Session; «Завершить эфир» — отдельная операция. Частичный результат не называется общим успехом.

«Сбросить отображаемые счётчики» использует локальные baseline по разделу 9.4. Сброс текущих серверных показателей, FFmpeg/GPU, истории или OBS internal counters не выполняется.

## 11. Пользовательский интерфейс: два окна

### 11.1 Компактный Dock (всегда в рабочем пространстве OBS)

**Название окна: «GOST Restreamer».** Dock не содержит вкладок «Обзор/Выходы/Профили», боковой навигации и настроечных форм. В верхней строке содержимого находятся селектор потока и справа от него текст состояния подключения без точки, прописными буквами во всех состояниях, включая отсутствие данных. Название продукта внутри содержимого и строка профиля OBS не повторяются. Шестерёнки в Dock нет. Пункт «Сервис → GOST Restreamer» открывает **одно** окно из раздела 11.2 (если уже открыто — выводит на передний план).

Макет принципиальный, цифры условные. Высота растёт со списком назначений: для ограниченной высоты Dock список выходов прокручивается внутри собственного блока, а ключевые состояния и основные кнопки остаются видимы. При узкой ширине 300–400 px табличные метрики переносятся внутри колонок; строки выходов остаются однострочными с сокращением длинного текста и полными значениями в подсказках. Шрифт не уменьшается до нечитаемого размера.

Композиция содержит четыре самостоятельных блока: «Состояние», «Статистика OBS»,
«Статистика потока» и «Статистика выходов». Их фон отличается от общего фона Dock, тонкая
граница и скругление около 6 логических px отделяют содержимое. Внутренние
отступы составляют 10–12 px, промежутки между блоками — 8–12 px с учётом DPI.
Выбор потока и текст состояния связи находятся в шапке. Внутри блоков «Состояние»
и «Статистика OBS» данные разделены на две колонки: каждая сохраняет пары подписей
и значений с переносом длинного текста. В «Статистике потока» формат, FPS
и битрейт входа расположены в трёх столбцах: подпись над значением, длинный текст
переносится внутри своего столбца. Эти данные не объединяются с локальными
OBS-измерениями. Счётчики OBS показывают значения и единицы без отдельной
строки периода и без подписей периода рядом с отдельными значениями.

В одной горизонтальной строке выхода находятся имя, независимый статус
и битрейт, справа — кнопка «…». Переподключения, очередь и два вида потерь
сохраняются в подсказке и доступном описании строки. Список содержит назначения
выбранного потока и до начала эфира; отсутствие исполнения не означает STOPPED
или нулевой битрейт. Пустой состав занимает высоту пояснения. Три пакетные
команды находятся рядом с заголовком как иконки без текста с локализованными
подсказками и доступными именами. Подписи «Исходящие потоки» нет.
Кнопка локального сброса расположена внизу Dock. Подсказка «Начните трансляцию…»
не выводится. Рядом со сбросом показана версия сборки в формате
`0.1.0+<короткий HEAD>`; хеш обновляется при каждой сборке модуля без ручного
изменения версии. При сборке без доступных метаданных Git суффикс — `+unknown`.

Под статистикой выходов нет отдельного развёрнутого текстового отчёта о командах,
включая неудачные, незавершённые и прерванные запуски. Модель текущих и прежних
результатов, безопасный ручной повтор и наблюдаемые состояния строк сохраняются.
Цель повтора доступна в подсказке существующей кнопки управления.

**Статус заглушки** до запуска основан только на доступных метаданных: `READY` не доказывает пригодность старой версии генератора T15 или физическую готовность дорожки. Только успешный запуск Session подтверждает серверную готовность на время данного исполнения. **Состояние OBS и входа** — независимые: OBS может передавать, а ingest ещё не быть авторизованным; при отключении OBS сервер может продолжать fallback. Входное `connected` не заменяет фактический `source` группы; несколько групп могут одновременно использовать разные источники. **Статистика OBS** берётся локально (раздел 6); **статистика входа и выходов** — из Go REST/SSE (раздел 8). Для каждого Output отображаются статус, фактический bitrate и reconnect; по необходимости кратко выделяется наличие `queue_drops`/`delivery_drops`, но подробные причины — в расширенной диагностике.

`[…]` напротив выхода — меню **«Запустить» / «Остановить» / «Перезапустить» / «Подробности»**. Индивидуальный запуск сохраняет три ветви раздела 9.3; Stop/Restart требуют точного attached Output в RUNNING Session. Отдельной паузы и пункта Detach нет. «Подробности» передают точные context+Destination ID и открывают настройки любой адресуемой показанной строки, включая каталоговую до эфира, в прежнем единственном ManagementWindow. Session/runtime не являются условием просмотра. Сохраняются парковка/восстановление черновиков и маски; исчезнувшая запись получает существующий отказ чтения, runtime-only строке без Destination не выдумывается адрес.

Перезапуск, пакетная остановка выходов и завершение эфира требуют подтверждения с безопасным ответом по умолчанию. Текст остановки выходов не подменяется предупреждением о завершении OBS/Session. Перед вложенным циклом меню/подтверждения фиксируются context, режим, Session/Destination/Output и полный показанный пакет; после — проверяются время жизни Dock и исходные цели. У заголовка три кнопки с иконками без текста «Запустить все», «Остановить все», «Перезапустить все», со смыслом раздела 9.3 и локализованными подсказками и доступными именами. Они не включают OBS; отдельное «Завершить эфир» останавливает OBS+Session. Пауза/завершение Session неактивны при подтверждённом её отсутствии. Неизвестность показывается как отсутствие данных. Отдельного UI проверки и предварительного запуска заглушки в редакторах конфигурации нет до согласования.

### 11.2 Расширенное окно «GOST Restreamer — Управление и настройки»

Открывается пунктом **«Сервис → GOST Restreamer»**; «Подробности» выхода используют то же окно. Пункт регистрируется через штатный `obs_frontend_add_tools_menu_qaction`, повторное открытие сохраняет экземпляр и выбранный раздел. При shutdown QAction удаляется синхронно до конца `OBS_FRONTEND_EVENT_EXIT`; удаление меню самим OBS учитывается через QPointer. «Настройки» и «Расширенные» размещаются в конце левой навигации единого окна. Пункты навигации имеют иконки из светлого или тёмного набора OBS. При недоступности ресурсов OBS используются стандартные иконки Qt.

| Раздел | Назначение и организация |
| --- | --- |
| **Потоки** | Список Streams, создать/переименовать/удалить, выбрать рабочий, назначить fallback-policy. В карточке — выбор нескольких собственных назначений для следующего эфира без технических ID и сводки групп кодирования. Раздел содержит только редактирование; управление текущим эфиром выполняется из Dock. Поле «Ключ трансляции» (`publication_key`) маскировано, доступны **Показать/скрыть** и **Копировать**, включая существующие Stream. Плагин не меняет RTMP-настройки OBS |
| **Выходы** | Список Destinations и карточка их настроек: создать/изменить/удалить, принадлежность потоку, группа, сервис, адрес и ключ. «Сохранить» меняет конфигурацию для следующего запуска без изменения Output текущей Session. Отдельных attach/detach, runtime-селектора, кнопок start/stop/restart, сообщений о прикреплённых выходах и блока заглушки здесь нет; текущими выходами управляет Dock. В карточке Destination поля **«Адрес трансляции»** (`endpoint`) и **«Ключ трансляции»** (`stream_key`) по умолчанию маскированы, доступны **Показать/скрыть** и **Копировать** |
| **Группы кодирования** | Самостоятельная страница: название, Stream и связанный профиль. Справочный список назначений с ID не отображается; связь назначения с группой задаётся в карточке выхода. Внутренних вкладок групп/профилей нет |
| **Профили** | Самостоятельная страница полного профиля по разделу 7.1. Основные поля без отдельной подложки и заголовка, расширенные настройки раскрываются по нажатию. Справочного списка групп с ID нет; видео и звук выбираются раздельно |
| **Заглушки** | Список Asset, загрузка изображения/видео, `rebuild`, current/pending Generation, статусы поколений и READY-варианты, назначение Asset к Stream; подпись «аудио оригинала не используется, fallback беззвучен» и памятка о rebuild после смены генератора T15 |
| **Диагностика** | Отдельные OBS-вход/серверный вход/группы/выходы; FPS, bitrate, очереди, потери; FFmpeg и NVML; `RTMP ACK` только по выбранному выходу, история Session и квитанции |

Выбор потока и состояние связи находятся в Dock. Язык и тема автоматически следуют OBS; отказы явных серверных операций показываются в общем диалоге по разделу 15 |

Общие кнопки «Сохранить» и «Отмена»; ввод не применяется до сохранения. Постоянная справочная подпись о журнале не отображается |

**Единый UX-контракт для ключей и адресов:** `Stream.publication_key`, `Destination.stream_key` и полный `Destination.endpoint` доступны при открытии соответствующей карточки. Каждый ввод отображается в виде `••••••••` по умолчанию; иконка глаза временно раскрывает значение, повторное нажатие скрывает. Иконка копирования помещает **полное фактическое значение** в буфер обмена даже в замаскированном состоянии, без автоматического показа. При смене сущности, закрытии/повторном открытии карточки значение снова замаскировано. Показ/копирование возможны и для ранее созданных данных после перезапуска OBS. Пустой `stream_key` обозначается как «Ключ не задан» с неактивным копированием. Пока сервер не поддерживает чтение, показывать «Недоступно в текущей версии сервера», не генерировать фиктивных значений. Один показ при создании не выполняет требование постоянного доступа. Это не добавляет новых окон или автоматической настройки OBS.

У Destination адрес и ключ редактируются непосредственно в этих полях,
без флажка замены и второго ввода. Маскирование — режим отображения реальной
строки, а не содержимое для PATCH. Неизменённые секретные поля отсутствуют
в PATCH, явная пустая строка ключа очищает его. Сервис выбирается по названию:
YouTube → `youtube`, Twitch → `twitch`, VK Видео Live → `vk`; иное сохранённое
значение не заменяется автоматически.

Участие назначения в следующем эфире задаётся только в карточке его потока
через `Destination.enabled`. Новое назначение создаётся с `enabled=false`;
его обязательные Stream и согласованная группа выбираются в карточке выхода.
Сохранение состава использует отдельные изменения назначений по их ревизиям,
продолжается при отказе отдельной записи и показывает результат для каждой.
Несохранённый выбор сохраняется; потерянный ответ сначала требует сверки,
`409` не разрешает молчаливую перезапись. Частичный список не доказывает снятия
выбора у неполученных назначений. Эти действия не запускают и не останавливают
Output текущей Session. Черновики страниц живут в RAM своего контекста
сервер/профиль OBS и сохраняются при переключении разделов.

Кнопки перечитывания карточки подписаны «Обновить» / `Refresh` и имеют иконку
обновления. Все подтверждения используют «Да»/«Нет» либо `Yes`/`No` по языку
OBS, сохраняя смысл ответов и прежнюю кнопку по умолчанию. Два постоянных
пояснения о штатной настройке OBS и автоматическом языке/оформлении на странице
«Настройки» не показываются; страница содержит адрес, сохранение/отмену,
локальную валидацию и предупреждение об отказе записи. Статус связи находится в Dock.

Редактор профилей использует полный явный профиль dev.8 по разделу 7.1: конечные зависимые селекторы, точные QP/CRF и разрешённые custom-контролы. Произвольной CLI и raw JSON UI нет. Переименование не отправляет профиль; полная замена проверяет ревизию и матрицу. Текущий эфир сохраняет прежний снимок, для будущего fallback нужен подходящий вариант.

В раздел «Настройки» **не** добавляются API-ключ, RTT, управление GPU/числом NVENC-процессов, настройки RTMP ingest, задержка включения fallback, автоматическое завершение Session по событию OBS, произвольные «медиа-настройки плагина» или API-сброс статистики. Эти функции не принадлежат плагину либо не подтверждены его контрактом.

### 11.3 Оформление и доступность

Значения статусов подключения к серверу и трансляции OBS выделяются полужирным
в Dock и «Диагностике». Зелёный означает активное подключение
или трансляцию, жёлтый — подключение или переподключение, красный — ошибку.
Для отключённого соединения, остановленной трансляции и отсутствия данных
используется обычный цвет текста темы.

Ошибки валидации и отклонённое сохранение выделяются красным, подтверждённое
сохранение — зелёным с учётом светлой/тёмной темы OBS. Смысл результата всегда
указан текстом: локальный отказ явно сообщает «Изменения не сохранены»,
потерянный ответ остаётся неизвестным результатом, частичный отказ не получает
цвет общего успеха. Полный путь ошибочного поля сохраняется внутри клиента. Форма показывает
понятное название параметра и локальную причину проверки; такие причины
переводятся по доверенному ключу. Структурированные причину и действие сервера
показывает только общий диалог обычным текстом. Секретные значения и `value` не добавляются в объяснение диалога; полученная диагностика отказа, включая присутствующие секреты, сохраняется в OBS log по решению владельца. Сырое тело не выводится в интерфейсе.
Активная трансляция в Dock обозначается как «OBS: трансляция идёт» / «OBS: Streaming».

Оформление следует текущей теме OBS 33 и её варианту. Фон блоков, границы,
текст и кнопки используют палитру и шрифт приложения и обновляются при смене
оформления без перезапуска плагина. Набор тем не ограничивается четырьмя
заранее заданными состояниями. Русские подписи, локализация `en-US`
и клавиатурная навигация обязательны. Язык берётся из локализации OBS,
отдельных переключателей языка и темы у плагина нет. Отказ явной пользовательской операции показывается одним асинхронным всплывающим окном: причина и известное действие — отдельные PlainText части. В Dock и настройках/редакторе server reason/action не повторяются; наблюдаемые состояния, локальная валидация и CAS-сравнение сохраняются. Развёрнутый отчёт команд в Dock не выводится. Нативная приёмка интерфейса выполняется
при системном масштабе Windows 100%; по решению владельца масштабы выше 100%
не проверяются и не входят в критерии приёмки задач и выпуска.
Зелёный/жёлтый/красный применяются
только для реальных состояний, а не для декоративных badges. Никаких

## 12. Конкурентность, ресурсы и жизненный цикл

- `QNetworkAccessManager` и `QNetworkReply` живут в известном Qt thread/event loop; запросы асинхронны. Синхронных `QEventLoop::exec()` или блокирующего ожидания REST из UI/OBS callbacks нет.
- SSE parser ограничивает размер накопленного фрейма и число обрабатываемых событий за цикл; превышение переводит клиента в явную ошибку/resync без бесконтрольного роста памяти.
- Длительные задачи (uploads) имеют собственную отмену, прогресс и ограниченные бюджеты; обычный HTTP timeout не применяется к SSE как к короткому запросу.
- Одновременно выполняется только один согласованный workflow start/stop для конкретной Session; несколько независимых output-команд не должны портить состояние друг друга.
- При закрытии OBS прекращаются принадлежащие плагину HTTP replies, subscriptions, таймеры и callbacks; закрытие **расширенного окна** не удаляет Dock/общий StateStore и не завершает эфир; закрытие интерфейса само по себе **не** останавливает серверную Session.
- После изменения выбранного сервера/OBS Profile не применяются запоздалые ответы старого API connection к текущему StateStore: все ответы маркируются локальным поколением подключения.
- При `OBS_FRONTEND_EVENT_EXIT` новые вызовы OBS API после возврата из callback запрещены; уничтожение UI/сети выполняется в допустимой фазе shutdown.
- Сборка не добавляет кодировщиков, вторых Output, скрытых thread-local FFmpeg или собственных медиаочередей.

Наблюдение, команды и конфигурация используют три экземпляра одного `APIClient`
с общим пределом REST4/32: наблюдение — 2 активных/16 ожидающих,
командный workflow — 1 активный/8 ожидающих, конфигурация — 1 активный/8 ожидающих. Это один стек Qt Network;
восстановление SSE отменяет только запросы наблюдения. Командный экземпляр
перенастраивается по логическому выбору сервера/UUID профиля/Stream, явному
отключению и shutdown. GET известной квитанции может завершиться без SSE,
но потеря связи прекращает новые шаги пакета без автоматического продолжения.

Текущий workflow и последний прерванный результат находятся в отдельной
value-модели `StateStore`; они не подменяют runtime-наблюдения. Действия выходов
исполняются последовательно. Новый пакет фиксирует до 10000 показанных строк,
хранит один активный шаг и не более одного неизвестного шага на исходную строку
в RAM, с исходными payload/ID/receipt/pin и результатами stop/start. Отдельный
token шага инвалидируется до отмены: callbacks прежней строки не меняют следующую.
Локальный отказ допускает следующую независимую цель только при доказанной
той же Session; общая утрата цели/связи закрывает остаток. Бюджет одного явного шага/ручного повтора — 60 с,
включая очередь и чтение квитанции/состояния с паузой 250 мс. Ручной повтор
сохраняет прежние ID, параметры и цель, получает новый ограниченный бюджет
и не возобновляет остаток прерванного пакета. Среди сохранённых Unknown выбирается
первый по исходному порядку, его имя обозначается существующей кнопкой/результатом.
Повтор stop не отправляет зависимый start и не завершает целый restart; успешный
повтор bootstrap не отправляет пропущенные add. Остановка OBS подтверждается
отдельно в пределах 5 с; недостоверная остановка остаётся неизвестной.

Конфигурационный контроллер владеет CRUD и RAM-черновиком независимо от видимости
окна управления. Create201/PATCH200 возвращают проверенную сущность, DELETE204
не требует JSON-тела. PATCH передаёт только явные изменения и точную ревизию;
Только `409` с `code=revision_conflict` требует сравнения исходной,
пользовательской и серверной версии. Отправленная
запись с потерянным либо недостоверным ответом остаётся Unknown без автоповтора.
До явной сверки смена карточки не снимает запрет следующей записи и precheck.
Адресный GET404 подтверждает нынешнее отсутствие, но не успех потерянного DELETE.
Неполный список не подтверждает удаления. Эпохи конфигурации защищают также
handshake списка Streams и предварительную проверку fallback от поздних ответов.

REST, ограниченный JSON-разбор и SSE reducer используют существующий GUI Qt
event loop. Отдельный QThread не создаётся; фактическая задержка на предельных
документах проверяется отдельно, жёсткая задержка в миллисекундах не обещается.
Политика клиента: HTTP absolute 15 с по умолчанию (настройка 5–60 с)/idle 10 с,
4 активных/32 ожидающих запроса;
SSE handshake 15 с/idle 45 с без общего lifetime timeout, read 256 KiB;
REST 8 MiB/anchor 16 MiB; frame 1 MiB; pending 4 MiB/256 событий.
За цикл — до 32 событий/256 KiB либо один проверенный крупный frame до 1 MiB
с передачей управления перед следующим. Полный список — до 100 страниц,
10000 элементов/64 MiB принятых страниц с явным признаком неполноты.
Очередной ответ проверяется по собственному пределу 8 MiB. Если он укладывается
в этот предел, но целиком не помещается в остаток общего бюджета, возвращаются
уже принятые страницы. Подключение продолжает получение снимка и подписку.
Из неполного списка в селекторе Dock можно выбрать полученные потоки даже в ожидании заголовков SSE.
Признак неполноты виден в сообщении Dock. Сохранённый поток за пределами списка
считается неподтверждённым, его привязка сохраняется.
Runtime ограничен 10000 узлами с явным resync при превышении.
Backoff 1–30 с с jitter, не более трёх стартов
за 10 с и затем cooldown. Upload требует отдельного бюджета следующего этапа.

## 13. Хранение конфигурации и доступ к ключам

| Данные | Где должны храниться |
| --- | --- |
| Streams/Destinations/Profiles/Groups/Fallback | Серверная SQLite через Go API |
| `Backend API URL`, UI-предпочтения | Локальная конфигурация плагина |
| Привязка «сервер + OBS Profile» → Go Stream ID | Локальная конфигурация плагина; отдельная запись для каждой пары, сохраняемая при переименовании профиля |
| RTMP Server, введённый пользователем в OBS | Штатные настройки OBS streaming service; плагин не меняет их |
| `Stream.publication_key` | Источник истины — серверный Stream в SQLite. Плагин получает значение через расширенное серверное чтение деталей, отображает замаскированным до явного раскрытия и предоставляет копирование; не хранит самостоятельную постоянную копию. В OBS пользователь вводит ключ вручную |
| `Destination.stream_key`, полный `Destination.endpoint` | Источник истины — серверная запись Destination. Контракт `103d839` возвращает точные значения; карточки читают их по мере необходимости. У старого несовместимого ответа отсутствие поля явно недоступно |
| Runtime cursor, активные сетевые requests и временные baseline | Оперативная память; baseline при сбросе относится только к текущей проверенной идентичности; не источник долгосрочной истины |
| История Session/квитанции | Серверная SQLite; текущие `request_id`, параметры и идентификатор квитанции хранятся в RAM живого workflow. После рестарта восстанавливается фактическое состояние по разделу 7.2; точный результат утраченной команды может остаться неизвестным |

Настройки плагина и привязки хранятся в пользовательском пространстве настроек OBS (например, через `obs_module_config_path()`) с атомарной записью (`QSaveFile` либо эквивалент) и версионированным форматом. Временные baseline видимой статистики живут только в памяти и не записываются в настройки. Не использовать глобальные пути `Program Files`/`ProgramData` для пользовательских изменяемых настроек. Изменение выбранного OBS Profile не должно без уведомления подменять серверный Stream: при смене профиля клиент перечитывает свою привязку, а OBS управляет своим сервисом и ключом самостоятельно.

Ключ привязки учитывает выбранный сервер и устойчивую идентичность OBS Profile; отображаемое имя профиля не служит единственным ключом. Переименование не создаёт новый профиль и не сбрасывает его привязки ни к одному серверу. Сохранение и восстановление после перезапуска OBS соблюдают эту идентичность.

Текущий формат настроек — ограниченный JSON schema v3, QSaveFile с
`directWriteFallback=false`. Поле `sse_rejection_retries` хранит целое число
повторов от нуля или `-1` для режима «Без ограничения». При чтении schema v1
используются три повтора, прежние настройки и привязки загружаются.
Поле `http_timeout_seconds` хранит целые5–60с (default15), `log_level` —
`normal` либо `detailed`. V1/v2 получают15с и обычный журнал без записи файла
при чтении. Новое HTTP-задание фиксирует срок; уже принятое не продлевается.
Неизвестный/повреждённый формат не перезаписывается;
отказ записи сохраняет прежний файл и рабочие значения RAM с уведомлением.
Прежние поля `auto_connect` и `reconnect` продолжают читаться и записываться для
совместимости schema v1–v3, но их значения не отключают штатное подключение и
восстановление текущего клиента. Элементов управления ими в интерфейсе нет.
Сервер — строгий HTTP(S) origin без userinfo/query/fragment и пути кроме `/`;
scheme/host/default port канонизируются, DNS alias и IP не объединяются.

Идентичность профиля — plugin UUID, а имя и путь — изменяемые атрибуты.
OBS33 rename создаёт новый каталог и отправляет Changed раньше Renamed,
иногда с вложенным диалогом между ними. Adapter захватывает имя/путь/inventory
в GUI callback. Changed без предварительного Changing, исчезнувшее старое имя
и новый locator распознаются как rename; UUID и все серверные привязки
переносятся атомарно. New/duplicate/recreated получают новый UUID. Неоднозначный
или foreign-thread переход остаётся явно unresolved. Ручные offline-перестановки
каталогов и crash посреди rename не восстанавливаются угадыванием.

Серверные журналы сохраняют согласованный локальный режим `full`. Клиент пишет в штатный OBS log, отдельный файл не создаётся. В обоих режимах «Обычный»/«Подробный» каждый новый отказ явной пользовательской операции записывается с кодом, описанием и полученной ограниченной диагностикой, включая присутствующие секретные значения. Это решение владельца отменяет прежнюю фильтрацию такой диагностики. Успешные тела, clipboard, полная конфигурация и дампы всех запросов не пишутся. Общие технические записи сохраняют закрытые категории и числовые измерения. Серверный текст передаётся как значение, не строка формата; диагностика не накапливается в истории всех строк workflow.

## 14. Безопасность и доверенные зоны

Плагин используется **только внутри доверенной локальной сети владельца**. Действующий контракт backend не требует авторизации REST/SSE; доступ к API в принятой архитектуре контролируется локальным контуром. Ключ публикации RTMP предназначен для приёма видеопотока и не служит авторизацией HTTP API.

- `Backend API URL` указывает на явно выбранный хост локального Go-сервера; кнопка «Сохранить» явно подтверждает применение нового адреса и подключение.
- При использовании HTTPS сохраняется штатная проверка сертификата Qt/Windows; игнорирование TLS-ошибок не допускается.
- Клиенты REST/SSE напрямую соединяются с указанным локальным сервером: у принадлежащих плагину QNetworkAccessManager установлен NoProxy. Это исключает блокирующее чтение системного proxy/WinHTTP до запуска таймеров запроса; общая proxy-конфигурация OBS не меняется. Проксирование удалённых серверов не входит в выбранный локальный контур.
- `Stream.publication_key`, `Destination.stream_key` и полный `Destination.endpoint` **доступны владельцу для чтения и копирования** в карточках соответствующих сущностей; при первом отображении они визуально замаскированы, а иконки глаза и копирования работают независимо. Маска не ограничивает доступ к API и не является шифрованием. Плагин не копирует значения автоматически; Windows clipboard после явного копирования доступен другим приложениям. Показ ключей в компактном Dock не требуется.
- Плагин не добавляет учётные записи и не меняет установленную backend-политику доступа.

## 15. Ошибки, восстановление и пользовательские сообщения

| Ситуация | Реакция плагина |
| --- | --- |
| Go API недоступен / timeout | `Не удалось подключиться`; не делать вывод об остановке существующего эфира; backoff/retry |
| `GET /health/ready` → `503` | Управляющая часть не готова; не заменять на статус «FFmpeg неисправен» |
| Ошибка TLS / проверка сертификата | Отклонить небезопасное подключение, показать причину |
| SSE `204` или постоянный отказ (например, `404` либо ответ `200` без типа `text/event-stream`) | Завершить автоматическое восстановление, показать безопасную причину |
| SSE `400` / `409` | Штатно получить свежий снимок и повторить подписку. По умолчанию три таких цикла после первого отказа. Начатый цикл учитывается и при сбое снимка. После успешного снимка временный сбой подписки возобновляет её с курсора этого снимка. Счётчик таких циклов сохраняется до подтверждения подписки или смены контекста. Число повторов настраивается, включая «Без ограничения» с обычным пределом частоты. Если нужен очередной цикл, а бюджет исчерпан, показать причину; явное повторное сохранение адреса начинает новое подключение |
| Команда `202` | Сохранить принятие в модели операции и ждать `GET /commands/{id}`; наблюдаемое состояние выхода остаётся самостоятельным |
| Перезапуск плагина при потерянном ответе команды | Перечитать текущие Session/Outputs и snapshot/SSE по разделу 7.2 без повторения POST. Недоступная прежняя квитанция оставляет результат старой команды неизвестным; неотправленные шаги пакета автоматически не продолжаются |
| Ошибка собственной квитанции / Session `FAILED` | Сохранить `failure.code/action/field/context`; один раз показать отказ собственной операции в общем всплывающем окне и записать диагностику в OBS log. Наблюдаемые состояния Session/выходов остаются независимыми |
| `409` конфигурации | Только `code=revision_conflict` включает перечитывание и сравнение/подтверждение CAS. Другие `409` сохраняют предметную причину; рост ревизии позднего GET не меняет код исходного отказа |
| `409` загрузки/rebuild fallback при работающей Session | Показать запрет подготовки во время эфира, не обходить серверное ограничение |
| `400/422` | Сохранить публичные пути и структурированные причины; отказ явной записи показать причиной и действием в одном диалоге, без повторения server reason/action в форме. Локальная валидация формы сохраняется. Полученная диагностика, включая секреты, пишется в OBS log по решению владельца |
| `resync_required`, старый epoch | Пересоздать runtime snapshot и SSE, не меняя эфира |
| OBS `STREAMING_STOPPED`, Session `RUNNING` | Показать fallback/потерю источника; не отправлять автоматический server stop |
| Ошибка/таймаут подключения OBS после принятого запуска | Перечитать Session: сервер может продолжать fallback; не создавать повторный start и не выполнять скрытый stop |
| Go Session `STOPPED`, OBS streaming active/переподключается | Сохранять независимые состояния OBS и точной Session в блоках Dock и перечитать активную Session. Результат Stop All в модели остаётся частичным или неизвестным до подтверждения остановки OBS; отдельный текстовый отчёт не выводится |
| Новый Session ID после рестарта/переподключения OBS | Подхватить подтверждённую Session выбранного Stream, сбросить привязанные к прежнему исполнению операции и baseline; не отправлять дополнительный start/resume |
| Нет наблюдения GPU/FFmpeg | «Нет данных/не подтверждено», не «0%» и не фиктивный отказ |

Однократное уведомление выпускает владелец явной операции после проверки context/generation/step; повторный polling или перерисовка StateStore его не создают. Runtime владеет одним асинхронным переиспользуемым диалогом с PlainText причиной и известным действием; новое сообщение обновляет открытое окно, каждый отказ отдельно пишется в OBS log. Пассивные чтения/reconnect не вызывают всплывающих отказов. До shutdown сервисов presenter отключается, диалог удаляется; скрытие ManagementWindow его не уничтожает. Диагностическое тело краткоживущее, ограничено HTTP-бюджетом и очищается до сохранения длительной value-модели. Остальные события журнала — идентичность операции, переходы FSM, HTTP-категория и reconnect/resync, без обещания успеха до подтверждения.

## 17. Windows-сборка и установка

### Разработка

1. **Visual Studio Code** как единственный необходимый редактор/IDE.
2. MSVC из **Visual Studio Build Tools**, Windows SDK, CMake, Ninja и Qt6/OBS SDK из совместимого комплекта.
3. `CMakePresets.json` содержит разработческий `windows-x64` и CI-профиль; комплект зависимостей/платформы закреплён в `buildspec.json` или эквивалентном lock-файле.
4. Официальный Plugin Template используется как основа CMake/CI, но его зафиксированные OBS 31.1.1 и preset Visual Studio generator пересматриваются до выпуска на OBS 33.
5. Debug (`RelWithDebInfo`) с символами и Release-пакет формируются воспроизводимо.

### Распространение

Для **OBS Studio 33.0.1** используется **новый официальный Windows ProgramData-формат** из OBS [Legacy Plugin Developer Info](https://obsproject.com/kb/legacy-plugin-developer-info), опубликованный 21.09.2026:

```text
C:\ProgramData\obs-studio\plugins\
└── gost-restreamer-obs-plugin\
    ├── gost-restreamer-obs-plugin.dll
    └── data\
        └── locale\
            ├── ru-RU.ini
            └── en-US.ini
```

Для дополнительных DLL-зависимостей путь упаковки и загрузка проверяются на чистой Windows-машине. Установщик и portable OBS имеют отдельные режимы размещения; запись файлов в рабочий каталог `Program Files\obs-studio\obs-plugins\64bit` не выбирается как основной способ. Для смены бинарной версии OBS необходимо завершить приложение (DLL не обновляется безопасно, пока загружена).

**Совместимость:** общая статья OBS [Plugins Guide](https://obsproject.com/kb/plugins-guide) 2022 года всё ещё описывает прежний путь `bin\64bit`, но отдельная актуальная инструкция разработчика для OBS 33 относит его к **Legacy**. Новая архитектура использует DLL непосредственно в корне каталога плагина. Это также относится к переносимой OBS, где каталог `plugins` находится в корне portable-установки; размещение и зависимости проверяются при выпуске.

### CI

GitHub Actions Windows runner: configure/build MSVC, unit/contract tests, проверка loadable DLL, zip layout, локализации, version metadata, публикация подписанных/проверенных checksums релизов. Цифровую подпись инсталлятора можно добавить после выбора сертификата и процесса релиза; не утверждать её наличие до реализации.

## 18. Тестирование и приёмка

**Исходная доказательная база:** принятое T11 подтверждает основной серверный медиатракт при конкретных профилях и примерно 10-минутном эфире OBS → сервер → YouTube/VK/Twitch, включая переход в fallback после остановки OBS. Этот прогон выполнялся **до изменений T15**; CI поставки `v0.1.0-dev.5` успешен, но не подтверждает новый LIVE AAC copy и беззвучные заглушки на целевой VM. Плагин на Windows в T11 **не использовался**; нельзя объявлять выполненными его UI, управление Session/Output, SSE, сброс счётчиков и массовые операции. Не требуется трактовать уже проведённый основной прогон как непройденную разработческую задачу сервера.

**Проверки, остающиеся для `gost-restreamer-obs-plugin`:** настоящий OBS 33.0.1 на Windows, его native API и локальные счётчики; управление Start/Pause/Resume/Stop и каждой отдельной Output-командой через квитанции; SSE snapshot/resync; сценарии `OBS STOP` при продолжающейся Session и возврат LIVE; загрузка и повторная подготовка заглушек; согласованность редактора полных профилей; отказ сети/рестарт backend; неатомарный массовый перезапуск. Системные и длительные тесты backend из списка отложенных T11 не должны называться уже пройденными.

### Контрактные/unit проверки без настоящего OBS

- Разбор SSE (частичные чанки, heartbeat, cursor, resync, invalidated epoch), bounded buffers, отмена и закрытие.
- Числовой REST/SSE и исходящие JSON-запросы: полный U64/I64, узкие типы, Duration, наносекунды, nullable signed out_time_us; значения выше2^53, математически целые формы, unsigned -0, лишняя ненулевая дробь, переполнение и большие экспоненты. Полный encoding без версии, явный live_audio_mode, UTF-8 без Base64; чтение ключей/endpoint остаётся точным.
- Все четыре ACK-поля Output в REST/SSE; отсутствие наблюдения, переполнение/насыщение, границы интерпретации.
- Асинхронные квитанции, повтор того же `request_id`, потеря ответа, частичные массовые операции, отсутствие двойного `start`/`restart`, смена Session посреди пакета.
- Потерянный `202` с перезапуском плагина: восстановление текущих Session/Outputs на существующем API без повторения POST. Недоступный результат старой команды не подменяется успехом; пауза и намерения выходов сохраняются, неотправленные шаги пакета не продолжаются автоматически.
- Появление созданной публикацией Session после пустого snapshot, подхват уже существующей `STARTING/RUNNING`, сохранение паузы и остановленных/отсоединённых выходов без собственной квитанции или дублирующих команд; конфликт предварительного запуска с публикацией OBS.
- Отказ остановки OBS при успешном server stop, новая Session после следующей публикации, таймаут OBS при продолжающейся Session и восстановление после рестарта backend. Команды прежнего эфира не применяются к новому; потеря SSE сама не меняет передачу OBS.
- Локальная статистика OBS: разные знаменатели пропусков, вычисление bitrate, переполнение/регресс, отсутствие output, смена экземпляра; **сброс только видимых счётчиков** с корректным baseline по идентичности.
- Разделение локальных OBS пропусков и серверных `queue_drops/delivery_drops`: ни одно не отображается как доказанная потеря кадров платформой.
- Навигация: отсутствие вкладок/настройки сервиса и шестерёнки в Dock, один пункт «Сервис → GOST Restreamer», одно повторно используемое расширенное окно, отдельные страницы «Потоки/Выходы/Группы кодирования/Профили/Заглушки/Диагностика/Настройки/Расширенные»; сохранение черновиков при переходах. Все состояния связи в шапке Dock — прописными буквами.
- Профили: полная замена versionless encoding, точные QP/CRF и их присутствие, все поддержанные video/audio/SDR/HDR сочетания, зависимости конечных селекторов, недоступные unknown значения и сохранение черновиков. Rename не отправляет профиль. Самостоятельные snapshots текущего Output сохраняются; полный desired рецепт и measured matcher проверяются отдельно, включая математический FPS, aliases и неограниченные level/tier.
- Карточки «Потоки» и «Выходы»: ключи и адрес Destination по умолчанию маскируются, глаз показывает/скрывает, Copy копирует точное значение **без** предварительного раскрытия; повторное открытие карточки/смена сущности снова скрывают; прежние записи доступны после перезапуска OBS; пустое значение и устаревший backend обрабатываются явно.
- Запросы и таймауты при закрытии окна и смене OBS Profile/Stream/сервера не применяют запоздалые значения к новому StateStore.
- Привязки Stream независимы для каждой пары «сервер + OBS Profile», включая совпадающие Stream ID на разных серверах; возврат к паре и перезапуск OBS восстанавливают её выбор. Переименование профиля сохраняет все его привязки без повторного выбора Stream.

### Интеграция Windows + OBS 33.0.1 + backend

1. DLL загружается/выгружается без crash, Dock закрепляется и сохраняет положение, «Сервис → GOST Restreamer» открывает/повторно активирует **одно** расширенное окно; пункт меню удаляется при shutdown.
2. Пользователь показывает/копирует `Stream.publication_key` в «Потоках», `Destination.stream_key` и полный `Destination.endpoint` в «Выходах», включая ранее созданные записи и после перезапуска OBS. Поля исходно маскированы, копирование не раскрывает их. RTMP Server и Stream Key для входа пользователь вручную задаёт **в OBS**; плагин не подменяет сервис и не включает второй encoder. Поля читаются существующими GET Stream/Destination закреплённого контракта; расширение backend API не требуется.
3. Обычная кнопка OBS запускает Session со всеми включёнными назначениями; Dock подхватывает её без REST start. После отдельного согласования интерфейса заглушек предварительный запуск подтверждается собственной квитанцией и `RUNNING`, оставляя OBS остановленной; последующий штатный старт OBS присоединяется к той же Session. В Dock кнопки запуска нет; ingest LIVE и независимые outputs подтверждаются наблюдениями.
4. Dock отображает реальные FPS, время рендера и пропуски render/encode/network OBS, FPS и битрейт серверного входа, статусы выходов, переподключения, битрейт и очереди. Подписи состояний и доступности измерений соответствуют разделу 11.3 для `ru-RU` и `en-US`.
5. Отдельный Output stop/start; перезапуск `stop→start`; массовый перезапуск — отдельные последовательные квитанции, частичный результат и подтверждение прерывания действующих соединений.
6. Сброс статистики меняет только отображаемые накопления; FPS/bitrate не обнуляются; серверные счётчики и метрики штатного OBS остаются без изменений.
7. `Pause/Resume` сохраняет штатную передачу OBS и переключает серверные группы LIVE/FALLBACK; обрыв источника не завершает Session автоматически.
8. Заглушки: upload/генерация/current/pending/rebuild, публикация вариантов, проверка точного поколения, отказ при профиле без подходящей подготовки; **видео со звуком создаёт беззвучный вариант**, старая `READY`-генерация до T15 требует rebuild, ошибка rebuild не допускает старый вариант; процент кодирования не выдумывается.
9. Смена полного профиля или live_audio_mode не перенастраивает текущую Session; требуется подходящая подготовка для будущих запусков. Базовый сценарий LIVE AAC copy/transcode и несовместимого AAC сохраняется; расширенные video/audio/SDR/HDR сочетания dev.8 требуют отдельных целевых проверок, исходники/локальные тесты не подтверждают аппаратный результат.
10. Потеря HTTP/SSE и рестарт сервера не создают ложный успех; неизвестный результат собственной команды восстанавливается через квитанцию. Проверить новую Session от переподключения OBS после рестарта, сохранение паузы/остановленных выходов при переподключении к прежней Session, таймаут подключения с продолжающимся fallback. Stop All прекращает OBS и завершает точную Session; при отказе остановки OBS и следующем автозапуске показывает частичный результат, не останавливая новый эфир старой командой.
11. Базовая цепочка реального OBS → сервер → три площадки и сохранение выходов после остановки OBS подтверждены **историческим T11 до T15** в конкретном ~10-минутном прогоне. Верифицировать изменения T15 на фактическом backend при интеграции с Windows/OBS 33.0.1 отдельно; проверить управление, восстановление SSE и выходов и дополнительные отложенные сценарии. Длительную устойчивость не считать подтверждённой.
12. Windows ZIP/installer и путь OBS 33 проверяются на чистой системе со штатными зависимостями и системным масштабом Windows 100%.

Наличие успешного CMake build и локальных тестов не заменяет фактическую OBS/FFmpeg/NVIDIA и live-приёмку.

## 20. Интеграционные решения и ограничения

1. **Окна:** Dock без вкладок + одно расширенное окно из «Сервис → GOST Restreamer». Никаких дополнительных «окон настроек плагина» или кнопок шестерёнки в Dock.
2. **Названия:** основное название UI — «GOST Restreamer». Формулировки «Go-сервер», «Go → площадки» и названия внутренних пакетов не употребляются в пользовательских статусах.
3. **Подключение:** в расширенных настройках только базовый HTTP API и локальное поведение клиента; RTMP Server/Stream Key **вводятся пользователем в штатной OBS**. На странице «Потоки» плагин отображает и копирует серверный `publication_key`, не перенастраивая streaming service.
4. **Состояние backend:** точка входа, HTTP API и ingest реализованы. T11 принял исходный медиопрогон OBS → сервер → YouTube/VK/Twitch до T15 (около 10 минут, конкретные профили и LIVE→FALLBACK при остановке OBS). Dev-поставка **`v0.1.0-dev.5+ccbca60acb5b`** прошла CI, но новые аудиосценарии T15 отдельно на целевой VM в найденных материалах не подтверждены. Работа Windows-плагина, REST/SSE-интеграция, выходные команды и отложенные сценарии T11 остаются отдельной проверкой.
5. **Статистика:** OBS измеряет свой вывод, Go измеряет серверный ingest/группы/Publisher. Пропуски рендеринга, кодирования, сети OBS и очередей сервера не объединяются в единый «потерянный кадр».
6. **Сброс:** интерфейс хранит baseline; backend и OBS не получают команд очистки внутренних счётчиков.
7. **Выходы:** `start/stop/detach` относятся к Output в Session. `Destination.enabled` относится к конфигурации; «перезапустить» и «все» — клиентоуправляемая последовательность без обещания атомарности.
8. **Fallback и запуск:** подтверждение подготовленного поколения != server-ready; сервер проверяет варианты/файлы и готовность групп при API-start и автозапуске от OBS. Штатную передачу запускает пользователь в OBS; предварительный серверный запуск заглушки не включает OBS, а его UI согласовывается отдельно.
9. **Профили:** полный versionless encoding и явный live_audio_mode, точные QP/CRF и матрица dev.8. Custom только из разрешённых контролов. Неизвестный исходный документ сохраняется для просмотра/rename; полная замена требует допустимого явного рецепта.
10. **Актуальность схемы:** контракт закреплён за dev.8 `252669d`. OpenAPI взят из `docs/openapi.json` ревизии `95f5245`, добавляющей только файлы схемы к той же реализации. SHA256 и происхождение находятся в `tests/fixtures/backend/provenance.json`, прежняя база dev.7 сохранена как история. Commit установленного сервера и live-совместимость отдельно не подтверждены.
11. **Fallback:** цифровая тишина выбранной поддержанной аудиопривязки, без звука оригинала. После обновления прежнего генератора нужен rebuild; READY не подтверждает физический допуск. Версия генератора из неподдерживаемого API не выдумывается.
12. **Официальная OBS-совместимость:** Windows x64, OBS 33.0.1, Qt6/OBS Frontend API; протестировать Windows installer и DLL placement по формату OBS 33.
13. **Чтение ключей и адресов:** конфигурационные и исторические DTO возвращают точные значения; runtime anchor/SSE их не содержит. В настройки они не пишутся. По решению владельца секретные значения, присутствующие в диагностике отказа операции, сохраняются в штатном OBS log. Это не создаёт редактора RTMP OBS.
14. **Автозапуск dev.7:** Session может появиться без команды плагина, в том числе после рестарта backend при переподключении OBS. Плагин подхватывает её без дублирующих команд. Полное завершение требует остановки OBS и точной Session; следующая публикация с тем же ключом может запустить новый эфир.
15. **Восстановление состояния:** после перезапуска OBS используется существующий REST/SSE API (раздел 7.2), без доработки backend. Результат утраченной команды может остаться неизвестным; текущий эфир отображается по наблюдениям, старые команды и пакеты автоматически не воспроизводятся.

Никаких неподтверждённых параметров RTT до площадок, процентов подготовки на сервере, API-ключей, управления GPU, таймеров fallback или автоматической остановки server Session по OBS STOP в проекте плагина не предполагается.

## 21. Архитектурные инварианты

1. **Два окна:** Dock и одно расширенное окно, доступное из «Сервис → GOST Restreamer»; Dock без вкладок, шестерёнки и форм конфигурации.
2. В UI продукт называется **GOST Restreamer**, без упоминания языка серверной реализации.
3. OBS остаётся единственным производителем видеопотока и владельцем штатного streaming service; плагин **показывает/копирует входящий ключ и ключи/адреса исходящих назначений** в расширенном окне (визуально маскируя их по умолчанию), но не меняет RTMP URL/ключ в OBS и не запускает второе кодирование.
4. Сервер владеет Session, Output, Profile, Group, Fallback, FFmpeg и достоверной оперативной телеметрией своего медиатракта.
5. HTTP `202` подтверждает принятие собственной команды: исполнение проверяется по квитанции и состоянию, публикация — по observations. Подхват серверного автозапуска опирается на состояние Session и observations, не требует выдуманной собственной квитанции.
6. OBS render/encode/network drops, серверные очереди и доставка — **разные метрики** и разные причины. Не отображать несуществующие RTT, packet loss до площадки, прогресс серверного кодирования либо гарантированное воспроизведение у зрителя.
7. У отдельного Output есть `start`, `stop`, `detach`; пакетные действия и restart составляются клиентом из них и показывают частичный результат.
8. Сброс видимых счётчиков не изменяет сервер, OBS или историю; FPS/битрейт и текущие статусы не сбрасываются.
9. Изменение полного versionless профиля и/или live_audio_mode не влияет на закреплённый Output и требует нового подходящего fallback-варианта. Rename не пересобирает исходный документ. Полный рецепт и фактический формат проверяются раздельно.
10. Никаких ложных нулей: `unavailable/stale/warming_up/saturated` и отсутствие snapshot отображаются отдельно.
11. `Generation ready` не означает реальную готовность fallback-группы или совместимость со свежим генератором: старые READY-варианты до T15 не воспроизводятся, необходим rebuild; фактическую готовность подтверждает серверный старт Session.
12. Пауза не равна OBS Stop, потеря OBS не завершает Session, потеря SSE не влияет на эфир.
13. Запросы асинхронны, Qt GUI не блокируется сетью; завершение расширенного окна не влияет на работу Dock и эфира.
14. Заглушки содержат цифровую тишину выбранной поддержанной аудиопривязки даже из видео со звуком. LIVE audio copy требует совместимого фактического формата, автоматического transcode при несовместимости нет.
15. Поддерживаются Windows x64/OBS 33.0.1 после приёмки; остальные платформы не являются гарантией.
16. Обычный запуск выполняется штатной кнопкой OBS. Индивидуальные и общие команды запуска выходов Dock не включают OBS; пакет ограничен показанной моделью. Подхват Session сохраняет паузу и намерения выходов. «Остановить все» относится только к выходам; «Завершить эфир» (внутренний StopAll) относится к точной Session/OBS и не подавляет будущие публикации с тем же ключом. Отдельный UI предварительного запуска заглушки отложен до согласования.
